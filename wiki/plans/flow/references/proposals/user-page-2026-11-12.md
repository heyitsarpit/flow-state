# What an app author will notice (2026-11-12)

Two cancel behaviours, both decided by the user on 2026-11-12. They replace the two outcomes the Spec review
raised: a cancel aimed at the request on the wire could hit the newer queued one, and a cancel admitted before a
success was processed still gave `unknown { Cancelled }`. The rules are @spec.WriteLanes.R14, @spec.WriteLanes.I40
and @spec.WriteLanes.I41.

## Q1 B: an exact cancel target (decided)

- **What happens:** `O.upload.cancel(album)` still cancels whatever request is current for that key. Add
  `{ attempt }`, a handle from the row view or the mapped event, and only that request is cancelled. If it has
  already ended, nothing changes and the cancel is recorded as `CancelMissed`.
- **What you will notice:** a Skip button that passes `{ attempt: event.attempt }` can no longer cancel the next
  queued upload by mistake. A queued upload has no handle until it starts.

```ts
Skip: { actions: [O.upload.cancel(album, ({ event }) => ({ attempt: event.attempt }))] }
```

## Q2 B: a definite answer beats the cancel (decided)

- **What happens:** if the server answers success or failure before the interruption takes effect, the machine
  hears that answer, its success writes apply, and the cancel is recorded as `CancelMissed`.
- **What you will notice:** `unknown { Cancelled }` now means only "the interruption won, so the request may or
  may not have landed". A Cancel click that comes too late shows the real result.
