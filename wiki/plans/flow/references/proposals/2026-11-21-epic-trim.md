## Proposed new `run` and `instructions`

```text
run
    To start: "run the loop in wiki/tasks/V3/epic.task". You are the orchestrator: you start, track and route agents;
    you never build.

    Start and resume by skill:build-a-loop#rules R1 to R7, R25 and R26: read, current Task, cron, real agent state,
    start note, one building lead, activity, keep the machine awake (for example `caffeinate -i` on this Mac). Project
    additions to R2: a Task in `review` comes first, and its independent check starts before any builder; a phase's
    Tasks stay `draft` until it starts; before its first Task starts, run R48's breakdown review, apply its re-splits,
    then write the next Task's full text with skill:to-task and open it; within a phase, follow its card's Order line.

    Rules: follow skill:build-a-loop#rules, skill:policy-delegation and skill:policy-verification at the library
    revision in skill; instructions override their defaults. The library is the Git repository
    `/Users/arpit/Developer/workflow/skills`, with the suite at `suites/workflow`; check its revision with `git -C
    /Users/arpit/Developer/workflow/skills rev-parse --short HEAD`, and if it differs from skill, read the pinned files
    from its Git history or ask the user.
instructions
    **Models and agents**

    - Opus leads and Haiku sidecars, Claude Code (detected 2026-11-09). Every lead runs at medium effort; Haiku review
      sidecars at high, read-only sweeps at medium (the user, 2026-11-14; overrides the effort defaults of R30
      and skill:policy-delegation).
    - Agents at once: one lead, building or reviewing, never both (the user, 2026-11-16; was one of each). The lead runs
      up to eight sidecars and decides how many and which jobs they do, never one per angle by default (the user,
      2026-11-14 to 2026-11-16). A review runs between builds: the builder stops at `review`, the review runs, then the
      fix round or the next Task. Extra work (merges, code-quality reviews) waits for the slot. Before starting any
      agent, the orchestrator reads the 5-hour window: above 80% only the current lead continues; above 90% it
      checkpoints and stops until the reset. Processes and browsers: the Constraints' serial-work line.
    - Haiku never writes or runs production code; it may run experiments or hill-climb in scratch files outside the
      package and submit ideas (the user, 2026-11-10 and 2026-11-15). A lead reads every line a sidecar wrote (the user,
      2026-11-08); re-running and logging results is skill:policy-delegation's.
    - A lead works through three context compactions and is rotated out only when a fourth is close: finish the step,
      commit, leave a resume note (the user, 2026-11-14).
    - Leads report once per batch or stop, in at most 10 lines: verdict, commits, test counts, and what needs a decision
      (the user, 2026-11-11).
    - Constraints: the Epic's Constraints section. Limits: its Limits section.

    **Building a Task**

    - Every brief carries the Constraints' code-style line (the user, 2026-11-09).
    - A Task's "May change" is a guide, not a fence: a Task may add its planted faults to `tests/faults.ts` and touch
      any file its acceptance needs, naming each extra file in a Task comment (2026-11-15).
    - Requirements first (the user, 2026-11-12), by skill:execute-task step 2. The requirements list is in the Task's
      comments, each rule with its source, mapped one to one to the Task's acceptance. The lead may gather it with
      read-only sidecars on named angles (the Specs and Plans; the code and prior art; open findings; an adversary).
    - The whole Task at once (the user, 2026-11-20): skill:execute-task step 1, with Task boundaries by skill:to-task
      step 1 and R48's phase-start review. The state's one owner function ships with its guard and its planted faults in
      the same Task; an implicit state machine spread across separate checks is a blocking finding.
    - A feature's benches are its fixture's `bench` entries, added with its Stories (the user, 2026-11-18).
    - Fixtures first (the user, 2026-11-16): a Task that builds or changes a public feature, or lands a review finding,
      meets @convention.fixtures as part of its requirements, before any code. The orchestrator owns it and checks it by
      asking the lead for that page's proof, never by reading the tests itself; a gap returns to the lead before the
      build, and the requirements review checks the proof, not the claim. Before posting the proof, the lead has
      sidecars review its fixtures against every part of that page: scenarios, load and structural stress, edge values,
      combinations, variety, real-shaped data, registration with every runner, and that each expected result is correct
      for its cited rule; the lead verifies and logs each finding (the user, 2026-11-16). Every Task with fixture work
      links the page in its acceptance, and every brief cites it too. What to build comes from
      @convention.fixture-catalog (the user, 2026-11-17): each Task's fixtures line names its migration step and
      fixtures; the lead builds those rows' scenarios from their cited sources, growing apps additively. Fixture counts
      are set from the bench and recorded in each Story; a count may change only by a recorded re-measurement (the user,
      2026-11-17, Q8 A). The catalog is a task list: at the close the lead marks every scenario item in those fixtures
      built (with its Story id) or left (with the later Task and the feature it needs), never leaves one unmarked, and
      corrects any row the build proved wrong; only a scenario needing a later Task's feature may be left, and the
      review checks each. The scenarios and their linked tests are best-guess guidance: the lead targets proper coverage
      and may add, reshape or replace scenarios, writing each change back as a catalog item.
    - Coverage before fixes and reviews (the user, 2026-11-17): a Task's bug fixing and its review wait until the
      fixtures its catalog step names are built, with every scenario written; a bug those Stories find lands as an
      inverted test with its owner Task, and is fixed by that owner against the full coverage.
    - A new rule is shown red on a planted fault: add the fault to `tests/faults.ts`, and `nub run faults --only
      <names>` must catch it; a Task plants only its own faults, by name, never the whole list. Plants go in a scratch
      copy, never the live tree.
    - A known bug is one inverted test (`it.fails`), titled by the Spec rule it breaks; `it.todo` is not used. A gap a
      review routes to a later Task lands as an inverted test, or as a comment on its owner Task when no fixture can
      express it yet (the user, 2026-11-12).
    - Which side is wrong (the user, 2026-11-12): before a red becomes a requirement or a fix, the lead replays it and
      names the wrong side with evidence: the runtime breaks a cited rule, or the test, the fake or the tooling does. An
      unknown is never given a default.
    - Spec contradictions (the user, 2026-11-12): the lead writes one concrete case with both results and decides a
      small or internal one itself, keeping the reading that loses no ending. Running code overrides a Spec, guarantees
      included, once the change is weighed across the whole system (the user, 2026-11-15): two traces of the same Story,
      every rule and reader that depends on it checked, and the next independent review confirms it was not shaped to
      fit the code; the user reads it afterwards. The Spec is edited so the losing text is gone, with one note
      in `wiki/specs/specs.log`.
    - A gap is never written into a Spec as a limit (the user, 2026-11-16): a lost, doubled or made-up ending the code
      can't yet meet lands as an inverted test titled by its rule, with an owner Task, and the Spec keeps the rule.
    - Lessons from the 2026-11-15 run (the user, 2026-11-16): comments are stamped only with `--now`; a gate counts by
      its exit code, never its summary line; a Task with its reviews costs about 2% of the weekly limit.
    - Plan changes found while building go to @plan.Pending as decisions, never into the Plans (the user, 2026-11-11),
      with the same whole-system check (the user, 2026-11-15).
    - Effect prior art (the user, 2026-11-11): each module's Spec skeleton lists the Effect features that cover its
      needs and why each is used or skipped. Adapters use typed failures, defects apart.
    - Speed (the user, 2026-11-14): batch independent tool calls in one message; launch a round's sidecars in one
      message; the package's suite (without the stress runs) may run whenever useful, and `nub run check` and that suite
      run before each checkpoint commit; a builder that needs a ruling states it and keeps doing independent work.
    - Big test commands run at the end of a Task (the user, 2026-11-16): the stress runs (stress Stories, their reload
      sweeps, generated stress seeds) sit behind a flag outside the default suite; they run once at a Task's close, in
      its review, and at a phase's close, never mid-Task. The whole `nub run faults` runs at most once a day (the user,
      2026-11-18) as a background process that blocks nothing: the first wake of the day starts `nub run faults
      --background` (few copies, lowest CPU priority) whether or not a lead runs, and no one waits on it; the next wake
      routes each missed fault. Timings taken while it runs are marked as such. Also at a phase's close; never in a
      Task's build or review.
    - Proof has a time budget (the user, 2026-11-18): any single verification step a lead or reviewer runs (a harness, a
      sweep, a matrix) is capped at 10 minutes; past it, it stops, reports what it has, and the orchestrator decides
      whether more is worth it. A review runs the suite once, alone, plus the stress runs only when the Task touched
      stress Stories or the sweeps.
    - At a Task's close the builder runs the stress runs and the generated Stories over fresh seeds; every new failure
      lands as a fix or an inverted test before review.
    - Earlier surfacing of what close reviews kept finding (the user, 2026-11-20):
      - a rule or Spec change the builder makes mid-build (skill:execute-task step 3) also gets two traces in a Task
        comment and one blind Haiku sidecar on that rule before the build goes on;
      - every requirements list names each real resource the Task touches (store, page, network, clock) and what its
        fake does not yet do (close, refuse after close, hold, hide); a gap is hardened in the fake or checked for real;
      - a Task touching a persisted shape shows restore after the definition is edited: a reorder, an add, a remove and
        a rename.

    **Reviews and done**

    - Reviews run on events, not on the clock (overrides R22): a Task's first commit, a Task's close, a Spec change, and
      a change to the test tooling or the run rules. One review sidecar is blind to the Task's requirements list (the
      user, 2026-11-12).
    - A requirements review has five fixed sidecars (the user, 2026-11-20), covering
      skill:check-task#at-the-requirements-review: blind A (requirements from the acceptance and Specs); blind B (from
      the proposal, catalog and routed comments, as an adversary hunting edge cases); flip A (red for its stated
      reason); flip B (the simplest wrong build); cohesion, which also lists the whole family up front (every export of
      the touched entries, every sibling of a changed type or helper) and every state with more than one writer. The
      lead checks the mapping and re-runs the cited reds itself; no suite re-run and no fixtures-proof re-check (the
      close review reads the fixtures).
    - A close review's one suite run is the coverage run (`nub run test:coverage`); one sidecar reads the uncovered
      lines and branches in the files the Task changed and names, for each, the Story or edge value that would reach it,
      dead code to delete, or a defect-only path (the user, 2026-11-20). No coverage percentage or baseline. Flip A
      re-runs on the Task's final checks.
    - A close review (R17) runs skill:check-task and reviews the Task's diff in the same pass.
    - Stopping rule (the user, 2026-11-12): a finding blocks only when it is in the Task's range, has a check red on
      current code, and is a lost, doubled, made-up or wrong ending, a hang, or a broken acceptance item; others are
      routed or noted. A fix round is checked by the next review, with no separate re-check.
    - Every accepted finding names why the tests missed it, by R17; its class is covered per @convention.fixtures, and a
      class that recurs across Tasks becomes a run rule or a fixture every later Task inherits (the user, 2026-11-16).
    - Convergence follows skill:policy-convergence (the user, 2026-11-20, after T57; the threshold for a local cause is
      2, the user, 2026-11-12; R35). Tests before convergence (the user, 2026-11-16): first every known behaviour of the
      part gets its fixtures, Stories and tests, the class shown red; only then redesign. On running code the freedom is
      taken away by structure (skill:policy-convergence#converging-live-code, the user, 2026-11-19, after T99).
    - When the daily `nub run faults` misses a fault, it lands as a run rule or a Story test, owned by the Task
      in range.
    - Every review checks the code it reads for outside imports, temporary names and what it re-creates of Effect; code
      quality is otherwise left to lint (the user, 2026-11-14).
    - Every requirements review and close review runs skill:check-task step 5 (cohesion) (the user, 2026-11-19), with
      this project's house patterns: tokens not strings, `$match` or tag tables, branded ids, `X.use`, Schema-derived
      types. One sidecar takes cohesion as its fixed angle.
    - A ruling is asked as two traces of the same Story, not as prose.
    - At each slice's close the orchestrator writes the user's page. A second slice may not close on an unread page (the
      user, 2026-11-12); that is in stops.
    - Benchmarks follow @convention.bench (the user, 2026-11-18): no agent sits blocked on a bench; `--dev` while
      working, every longer run capped and in the background; a Task's close runs no bench by default, and a performance
      Task records the quick tier once at its end, its review reading `--summary`.

    **Records and commands**

    - An Epic note is 1 to 3 lines; a Task comment is a verdict, the decisions that still matter and their reason (the
      user, 2026-11-11). No progress comments, commit lists or test counts beyond the one revision verified.
    - Command time limit: 5 minutes each (memory, 2026-11-04).
    - No worktrees (the user, 2026-11-08): the builder works in the main checkout on `flow-rewrite`.
    - No agent reads agent transcripts (the user, 2026-11-15).
```
