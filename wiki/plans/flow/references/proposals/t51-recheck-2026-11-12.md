## The four findings

1. **`ready()` after dispose: fixed.** `host/runtime.ts:224` checks `closed()` (not Open, so Disposing too)
   before the shared Exit. Red on the old code: once booted, `ready()` returned `Deferred.await(booted)`, a
   success, so `assert.throws` at `host/lanes.test.ts:828` failed. Spec note: this overrides Actors I3 ("every
   caller observes the same Exit") after dispose; R22 is explicit, so the Spec should say so (revisit).
2. **Held head pinned: fixed.** `host/lanes.test.ts:626-641` asserts the lane's head is still `Held` with the
   same Attempt, nothing new is sent, and a second `Ring` ends `failure Rejected` with no Attempt. A keep-and-drop
   runtime leaves no lane and fails at :627. The code was already right (`core/cells.ts:299`,
   `core/lane-moves.ts:304`).
3. **Lane-less ending kept: fixed, and the narrowed scope is right.**
   - The minted id is deterministic: `tx.mint("kept")` gives `kept-<seed>-<counter>` (`core/tx.ts:109-113`),
     with the boot's seed from the host. No clock or randomness.
   - No lane rule breaks. `Keep` on an absent lane is the `Idle` row, `keep` (`core/cells.ts:290`), so only the
     `kept` map and its record change (`core/persist.ts:135-145`). No lane is created, and no real key's lane id
     can equal `…|kept-…`, so it blocks no key. After a boot the restored ending carries the minted id as its lane
     (`core/record.ts:208`); `admit` finds no lane there and does nothing (`core/lanes.ts:234-251`).
   - No double delivery: a start delivers each kept ending once with `Tries.Last` and unkeeps it first
     (`core/incarnations.ts:106-115`). A third refusal re-keeps it under a new id, which is R15's "one try per boot
     or adoption".
   - Actors I24 requires it: after the second refusal the ending must survive "while its lane or life stands" to
     get its next try. Losing it at once broke that. The lead's claim that a Rejected decline was already kept is
     true, since it carries its lane (`core/lane-moves.ts:207-218`), but see route 1.
   - A read's answer is dropped, not kept. R15's "stranded" state and its evidence are unbuilt and already logged
     for the user (V3 log, 2026-11-09, @plan.Runtime.O4), so dropping is observably the same today.
   - Red on the old code: `keepEnding` did nothing without a lane, so `declined(seen).slice(4)` at
     `host/lanes.test.ts:679` was `[]`.
4. **Dispose during bootstrap: fixed; meets Actors R4.** `host/runtime.ts:213` fails `RuntimeDisposed` before
   `Boot`, so `open` stays false, no handle exists and `ensureActor` rejects. The boot stays uninterruptible: an
   acquisition in flight finishes, and the closed Scope runs its finalizer at once (Effect's
   `scopeAddFinalizerExit` on a Closed scope, `node_modules/effect/src/internal/effect.ts:4026`). That is R4's
   "a service acquired late is released". Red on the old code: the boot succeeded (the driver dropped `Boot`,
   `host/driver.ts:164`), so the join gave `booted`, not `RuntimeDisposed`.

## Non-blocking

- **Dispose while storage loads still starts acquiring services** (same surface as finding 4). With an async
  `store.load`, a dispose during the load is not seen until after `Layer.buildWithScope`
  (`host/runtime.ts:194-211`), so every service is acquired fresh after dispose, then released. R4 says the
  bootstrap is cancelled. Fix: the same `closed()` guard before the Layer build, with a case whose load is pending
  at dispose. Recommended for T51's next touch or T18; not a close blocker, since the outcome R4 names (no actor,
  no handle, services released) holds.
- **Weak assertions** (adversary, verified):
  - case (b), `host/lanes.test.ts:644-684`, turns the jam off before the adoption, so it cannot tell one try per
    adoption from many. It also never checks that `world().kept` is empty afterwards.
  - case (c), :686-711, shows the answer is not delivered, not that it was stranded. It asserts no restart of
    `peek` on the second attach.
  - case (e), :831-875: `Incarnated` cannot fire with an empty store, so "no actor starts" is vacuous. Only the
    `RuntimeDisposed` join is the red assertion.
  - case (d), :817-829, awaits a full dispose, so the Disposing window is untested. The predicate covers it.

## Gaps to route (all present before T51 started; none blocks it)

1. **A second kept ending on one lane overwrites the first** (Actors I24). `keep` writes a one-element list
   (`core/persist.ts:135-145`), as at 909f4bee. T51's `Keep.Held` row widens its reach. A Held head's kept unknown
   is replaced by a twice-refused Rejected decline on the same lane. The head is still re-announced as
   `unknown Restored` at the next start (`core/incarnations.ts:117-125`), so the author's unknown value and reason
   are lost, not the ending. Route to T18 with a failing case.
2. **Never-sent heads drop their lane at disposal**, against Actors I29 and R22's "no lane is dropped", while
   R22 also says a definite ending drops its head (`core/cells.ts:304-306`, `core/persist.ts:121-124`). The
   Specs disagree, so this goes to the Spec owner (revisit).
3. **Schema validation of records runs after services are acquired** (Actors I4). JSON is parsed before
   (`host/runtime.ts:195-204`), but records decode in the `Boot` step (`core/record.ts:174-277`). The comment at
   `host/runtime.ts:192` overstates it.
4. **`disposeActor` waits for the capture window** instead of flushing at once (Actors R20).
   `core/incarnations.ts:272` uses `Due.Later()`.
5. **Lane-less queued endings are dropped at disposal start** (`core/disposal.ts:25-26`). Reachable only past the
   10,000 drain cap. Low.
6. **Kept endings of a local life survive `disposeActor`** (R15 says they end with a local life). `dispose` lets
   kept endings go only when forgetting (`core/incarnations.ts:274-290`). Lane-less ones now join this.
