# Rules on machines (2026-11-20)

**Bottom line:** an app author writes rules beside their machine, and every run judges them. Rule coverage shows
which rules no run exercised, so an unexercised rule is never mistaken for a passed one. This file holds only what
the user has accepted.

## Accepted

- **Two rule kinds** (the user, 2026-11-20):
  - `invariants`: true at every publication.
  - `turns`: true of every accepted turn, given the snapshot before and after it.
- **Subjects** (the user, 2026-11-20): an invariant may name `in: S.X` and a turns rule `on: E.X`. A rule is
  exercised only when its subject comes up; a rule without one is exercised at every publication or turn.
  `in: S.SHIPPING` holds in `SHIPPING` and every state below it, as `S.SHIPPING.is` already means.
- **Only accepted turns** (the user, 2026-11-20): turns rules are judged and counted on accepted turns only; a
  denied or unhandled turn changes nothing and is neither judged nor counted in rule coverage.
- **Reloads** (the user, 2026-11-20): a restore publishes but is not a turn, so invariants judge the restored
  snapshot and turns rules skip it. A pair across a reload is not judged: saves coalesce, so the last captured
  snapshot may be older than the last published one.
- **A turns rule sees its event** (the user, 2026-11-20): when a turns rule names `on: E.X`, its check also gets
  `event`, typed as X's payload; without `on` there is no `event`.

  ```ts
  SetLandsInBounds: {
    on: E.Set,
    check: ({ event, after }) => after.memory.value === clamp(event.value, after.memory.settings),
  },
  ```
- **What a rule reads** (the user, 2026-11-20): what a guard reads: `state`, `memory`, `props`, `operations` and
  `schedules`. Only turns rules also read `context`, as the turn saw it (`before.context`): a consumer's context
  changes a publication before its own state and memory react, so an invariant linking them breaks on correct code.

  ```ts
  BeginOnlyWhenCartIdle: { on: E.Begin, check: ({ before }) => !before.context.busy },
  ```
- **Typed tokens, no magic strings** (the user, 2026-11-19): rules use the machine's `S`, `E` and `O` tokens and live
  where those exist, in the `machine()` callback.
- **Words** (the user, 2026-11-20): `turns`, not `transitions`, since the rule is judged on every accepted turn
  and "transition" already means a handler's `target`; "broken", not "breach", everywhere (`expectBroken`,
  `RuleBroken`, and Flow's run rules' `breaches` becomes `broken`).
- **Rule names** (the user, 2026-11-20): rules have their own namespace under `rules`, apart from states, memory and
  operations. A name is unique across `invariants` and `turns` in one machine or fragment: a duplicate is a
  type error at its key, and `machine()` refuses it at construction for casts and plain JavaScript. A type spike
  under `strict` showed the error fires at the duplicate and leaves each check's input inferred; the build repeats
  it against the real `machine()` signature.
- **Every run judges** (the user, 2026-11-20): every Story, generated run, reload sweep and pair sweep, with no extra
  call. A broken rule fails the run with the shortest Story that shows it.
- **Rule coverage** (the user, 2026-11-19; reframed 2026-11-20): the test run reports how often each rule was
  exercised and how many of all rules were, like code coverage; a rule no run exercised is listed as unseen, never
  as passed. Unseen is a measurement, not a failure: it never fails the suite, and nothing marks a rule as allowed
  to be unseen. Rule coverage is computed by the run, never stored, so `flow check` does not show it.

  ```text
  Rule coverage  12 of 14 exercised (86%)
    unseen  Number/Stepper.HoldStartsAtValue    in HOLD_REPEAT, never reached
    unseen  Desk/Editor/uploads.CancelSticks    Upload never placed
  ```
- **Checking is switchable, never silently** (the user, 2026-11-19): in Stories and runs, for Flow's own tests and
  users' alike, a rule is checked (default), expected to break (the Story passes only if it breaks), or off. The
  switch works per rule by token and for all rules, and rule coverage lists every rule expected or turned off.
- **The switch on a Story** (the user, 2026-11-20): a chained `.rules({ expectBroken, off })` that holds for the
  whole Story wherever it is written, so Story helpers can add it. A rule's token is `machine.rules.<Name>` or
  `fragment.rules.<Name>` (every placement). `expectBroken` passes only if each named rule breaks at least once;
  `off` (a list, or `"all"`) is not judged and does not count as seen; a rule in both lists is refused. Generated
  runs and sweeps from the Story inherit its switch.

  ```ts
  export const pastMax = numberStory("number-input/past-max")
    .rules({ expectBroken: [StepperMachine.rules.WithinBounds] })
    .send(quantity, Stepper.E.Set({ value: 99 }))
  ```
- **Flow's own run rules** (the user, 2026-11-20): the runtime's guarantees, which no app can break and no machine
  declares, get the same three modes only in Flow's own test helper, named by the rule value, never a string:
  `checked(run, { off: [everyCommitEndsOnce] })`. They are never public tokens and never in a Story's `.rules`.
- **Inline, opted into outside tests** (the user, 2026-11-20): rules stay inline in `machine()`, so every Story,
  sweep and tool finds them with the machine and needs no registration. Outside tests a rule runs only if its own
  `enabled` flag says so, which the user controls by any value (dev or production); off by default. Tests judge
  every rule whatever `enabled` says; there the Story switch decides. `enabled` is a boolean, fixed when the module
  loads (an env check such as `import.meta.env.DEV`), so `flow explain` can show it.
- **A broken rule outside tests is reported, never thrown** (the user, 2026-11-20): the host judges enabled rules after
  each publication, and a broken rule becomes a `RuleBroken` evidence record that inspectors and logs receive; the app
  carries on. The core never calls a rule.
- **Unreachable subjects** (the user, 2026-11-20): `flow check` warns `RuleSubjectUnreachable` when the compiled
  graph cannot reach a rule's `in` state or no reachable state handles its `on` event. Guards make the graph an
  over-approximation, so the warning is never false; a warning, not an error, so a machine mid-edit still checks.
  It separates "impossible" from "not tested yet", which rule coverage alone cannot.
- **Terminals** (the user, 2026-11-20): `terminals` lists state tokens, leaves or compounds at any depth, that no
  edge leaves. A leaf allows only a self-transition; a compound allows moves inside its subtree. Handlers on
  ancestors count, and in a subroutine so do exits. `flow check` proves it over the compiled graph: an edge out is a
  `RuleBroken` error, an empty list or a state listed twice is refused, and a listed state is never warned as
  likely stuck. Being about the graph, terminals are proved, not judged by runs, and the switch and `enabled` do not
  apply to them. Every event source counts: user events, `onContext` reactions, schedules and late operation
  endings. Restarts are not edges: a new incarnation, a restore or a trait's `resetOn`. A terminal pins the state
  only; memory may still change, and a `turns` rule claims more. It lives in `rules`, not on the states list: it is
  a claim, not shape, and it changes no behaviour.

  ```ts
  // states: ["PENDING", { SHIPPED: ["IN_TRANSIT", "DELIVERED"] }, "REFUNDED", "CANCELLED"]
  rules: {
    terminals: [S.REFUNDED, S.CANCELLED, S.SHIPPED.DELIVERED],
  },
  ```
- **Tools** (the user, 2026-11-20): `flow explain` lists each machine's rules; the test reporter prints rule coverage.
  Its exact format is settled in the build.

```ts
// existing: definition, machine, S, E
// NEW: rules, invariants, turns, in, on, check, enabled
// user-defined: WithinBounds, CommitMovesByOne, HoldStartsAtValue, inBounds

export const StepperMachine = machine(Stepper, ({ S, E }) => ({
  default: S.IDLE,
  on: {/* existing, unchanged */},
  states: {/* existing, unchanged */},
  rules: {
    invariants: {
      WithinBounds: {
        enabled: import.meta.env.DEV,                  // runs in dev too; tests judge it regardless
        check: ({ memory }) => inBounds(memory),
      },
      HoldStartsAtValue: {
        in: S.HOLD_REPEAT,
        check: ({ memory }) => memory.started !== null,
      },
    },
    turns: {
      CommitMovesByOne: {
        on: E.Release,
        check: ({ before, after }) =>
          after.memory.lastCommit.seq === before.memory.lastCommit.seq ||
          after.memory.lastCommit.seq === before.memory.lastCommit.seq + 1,
      },
    },
  },
}));
```

## Fragments

Accepted (the user, 2026-11-20); built with fragments and `Story.fragment`.

- A `trait` or `subroutine` body holds the same `rules` block as `machine()`; placing the fragment brings its rules,
  and a host may add rules but never remove or weaken one.
- A fragment's rules read only what the fragment declares: its own memory, operations and schedules, and for a
  subroutine its own states. Never props, context or the host's data. Subjects are its own `S` and `E` tokens.
- Rules are judged while the incarnation is live, on each placement and each `.each` copy separately; a frozen
  `.resumable()` trait is not judged.
- `Story.fragment` judges them alone; host Stories judge them where placed. Rule coverage names the placement
  (`Desk/Editor/uploads.CancelSticks`), a broken rule also names the copy (`uploads[a]`).

```ts
// existing: trait, definition, machine, Flow.input, Flow.initial, .each, raise, Story.fragment, Story.machine
// NEW: rules in a trait body
// user-defined: Upload, CancelSticks, RefNeverChanges, Editor, EditorMachine, Attach, CancelAll, attachments,
//   uploads

export const Upload = trait(
  {
    id: "Upload",
    events: { Cancel: {} },
    memory: {
      ref: Flow.input(Schema.String),
      cancelled: Flow.initial(Schema.Boolean, false),
    },
  },
  () => ({
    on: { Cancel: { target: "self", updateMemory: () => ({ cancelled: true }) } },
    rules: {
      turns: {
        CancelSticks: ({ before, after }) => !before.memory.cancelled || after.memory.cancelled,
        RefNeverChanges: ({ before, after }) => before.memory.ref === after.memory.ref,
      },
    },
  }),
)

export const Editor = definition({
  id: "Desk/Editor",
  states: ["EDITING"],
  events: { Attach: { ref: Schema.String }, CancelAll: {} },
  memory: {
    attachments: Flow.initial(Schema.Array(Schema.Struct({ ref: Schema.String })), []),
  },
  traits: { uploads: Upload.each({ of: "attachments", by: "ref", max: 10 }) },
})

export const EditorMachine = machine(Editor, ({ S, E }) => ({
  default: S.EDITING,
  on: {
    Attach: {
      updateMemory: ({ event, memory }) => ({ attachments: [...memory.attachments, { ref: event.ref }] }),
    },
    CancelAll: { raise: [E.uploads.Cancel] },
  },
}))

// The fragment alone: Upload.CancelSticks and Upload.RefNeverChanges, seen 2 each.
export const uploadAlone = Story.fragment(Upload, { id: "upload/alone" })
  .enter({ ref: "file-1" })
  .send(Upload.E.Cancel({}))
  .send(Upload.E.Cancel({}))
  .leave()

// The host: Desk/Editor/uploads.CancelSticks and .RefNeverChanges, seen 2 each (copies a, b).
export const twoUploads = Story.machine(EditorMachine, { id: "editor/two-uploads" })
  .send(Editor.E.Attach({ ref: "a" }))
  .send(Editor.E.Attach({ ref: "b" }))
  .send(Editor.E.CancelAll({}))
```

## Cut

- `eventually` (the user, 2026-11-20): Flow has no defined end of a run that ran its course; a Story may hold a call
  or leave a timer armed on purpose. A `turns` rule with `on` the turn that should clear a value covers most
  cases.
- `relations` across actors (the user, 2026-11-20): it needs an actor-query API only to state a claim.
