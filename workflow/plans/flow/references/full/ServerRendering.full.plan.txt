plan ServerRendering
title   Server rendering and hydration
status  proposed
goal
    Render Flow State views on the server and hydrate them in the browser without a mismatch,
    without a duplicate fetch and without replaying work. A server component calls dehydrate from
    flow-state/server, which owns one private request Runtime, waits a bounded time for it to go
    quiet, and captures one consistent cut into a Schema-encoded, JSON-safe, size-bounded payload.
    A client component <Hydrate payload> from flow-state/react makes that payload the only input of
    the first render (the no-mismatch rule H1, @O4) and, after commit, merges it into the live
    browser Runtime under fixed precedence (@O5). Next.js App Router with streaming is the primary
    host (@O7); plain React SSR uses the same three calls.

    This Plan owns the server and hydration contract: dehydrate, settle, the payload, Hydrate,
    precedence, isolation guards, Next.js integration and the evidence they emit. It reverses the
    SSR clause of FlowState D50 and the "SSR hydration is out of scope" sentence of FlowState O7
    (owner decisions 30 and 33). The adopted design is references/design/server-rendering.md; it
    holds rationale, worked examples and prior art. Where it and this Plan differ, this Plan wins.
    The hooks' first-render value outside any payload is @plan.React.O2; lazy entries in payloads
    are @plan.LazyFeatures.O4. Provenance per archived row is references/ledger/ServerRendering.md.
outcomes
    O1  dehydrate and the request Runtime
        flow-state/server exports exactly one name:

        dehydrate(setup, prepare, { scope, within, maxBytes? }): Promise<Hydration<A>>

        - **setup**: a RuntimeSetup<A> without persistence. Passing one with persistence is a type
        error and, for untyped callers, rejects with FlowError(DehydratePersistentSetup) before
        anything is constructed. A server KeyValueStore shared between requests would leak across
        requests, and a per-request store gives nothing because the Runtime is gone before
        dehydrate returns.
        - **prepare(runtime)**: synchronous, typed to return void, called once with a ready
        Runtime. It may use only the host surface: ensureActor, createActor and send on handles.
        A returned thenable or Effect rejects with FlowError(DehydratePrepareReturnedWork) after
        disposal; nothing from it is awaited. A throw disposes the Runtime and rejects with that
        error; a FlowError passes through unchanged, any other value becomes the FlowError cause.
        - **scope**: the principal the data belongs to; required; it follows the persistence scope
        rule of @plan.Persistence.O1 (non-empty, same bound). The host derives it from its own
        server-side authentication, never from request input.
        - **within**: the settle bound (@O2), a Duration.Input; required, no default (FlowState
        D34 style); it must be finite and greater than zero.
        - **maxBytes**: the encoded size bound (@O3); an integer from 1 to 2,097,152 (the shared
        codec's 2 MiB canonical bound); default 262,144.

        Invalid options reject with FlowError(DehydrateOptionsInvalid) before construction.

        The call, in order: validate options; construct the private Runtime from setup; await
        ready(); run prepare; settle (@O2); capture (@O3); dispose; resolve with the payload.
        The Runtime never escapes the call, so a server component cannot cache it, share it with
        another request or forget to dispose it. Two dehydrate calls on one page are two Runtimes;
        deduplicating their service calls (a request-scoped cache() around the HTTP client) is the
        service Layer's job, not Flow's.

        Failure and disposal:

        - A readiness failure rejects with the readiness FlowError after disposal.
        - Disposal is the bounded runtime.dispose() of @plan.Runtime.O6: lookups and stream
        sessions are interrupted, commits in flight are awaited up to the dispose bound and then
        recorded unknown, finalizers and evidence complete before the Promise settles.
        - When the call fails and disposal also fails, the rejection is one FlowError whose cause
        holds both failures (prepare or capture first, disposal second), as the frozen
        package's request-runtime wrapper did. A disposal failure after a successful capture
        rejects; no payload is returned from a Runtime whose cleanup failed.
        - The request Runtime never selects browser tab coordination: it runs with the solo
        TabCoordination Layer (@plan.MultiTab.O8), even where the host exposes BroadcastChannel or
        navigator.locks.

        Hydration<A> is opaque, branded, JSON-safe and serialisable as a React Server Component
        prop. Authors never write its type or read its fields.

        Server-side decisions such as redirect() or notFound() call operations or services
        directly in server code, never actors: dehydrate accepts no host-owned Runtime and exposes
        no actor state to the server component (@D2).
        Reference: none yet (stage S10 adds it).
    O2  Settle
        After prepare returns, dehydrate waits on the request Runtime's Clock until the Runtime is
        quiet or within has elapsed, whichever is first. Quiet means all three hold at one
        published cut:

        1. Every mailbox is empty and no turn is running.
        2. No finite lookup is in flight for any active lane, including chained activities that
        read earlier lanes, entity repair lookups and confirming reads (@plan.EntityDomains.O1).
        3. No commit is in flight and no outcome delivery is pending.

        Schedules and stream sessions never count toward quiet: a poll or live feed would hold the
        Runtime open forever. Quiet is evaluated after every publication, so a chain such as user,
        then org, then permissions settles as a whole.

        Capture takes the first quiet cut, or the cut current when within expires. Expiry is not an
        error: the payload records what was still pending (lanes without data, dropped mailbox
        events by actor and count), and one DehydrateUnsettled diagnostic goes to attachInspector
        sinks and the host log. A slow API costs the client one fetch; it does not fail the page.

        Production has no turn budget (owner decision 1), so a send cycle that never empties its
        mailboxes ends at within like any other unsettled work.
        Reference: none yet (stage S10 adds it).
    O3  Payload
        Selection: every shared actor in the request Runtime, plus the transitive closure of their
        context providers, plus the store data that the active lanes of any actor reference
        (local actors made in prepare included). Local actors themselves are never transferred:
        they have no address, and a client useActor always makes a new one. persist flags do not
        apply; hydration is a transfer, not durability.

        What each item carries:

        - **shared actor**: ref id and machine id; state path; memory encoded with the
        definition's Memory Schema; each activity binding (declaration slot, descriptor, canonical
        key, and the entry version it last mapped to a value outcome); each armed schedule's
        remaining time and restartOn baseline; the actor's own pending-commit facts exactly as
        persistence captures them (@plan.Persistence.O3). Never mailbox contents, issues,
        placeholder previous values, fibers, sessions or input.
        - **context**: nothing. Context is recomputed from the hydrated providers on both sides.
        - **resource entry**: canonical key, data encoded with the resource's result Schema, age
        at capture, generation. Never optimistic layers, failures, errors or defects.
        - **stream lane**: the latest value encoded with the stream's value Schema, and the count.
        Never the session or buffered values.
        - **entity record**: the confirmed fields that transferred answers project, each with its
        version. Never predictions, queues, tombstones, uncertain marks or positions.
        - **entity answer**: input, references or pages, hasMore, and whether it was stale at
        capture. Never frontier positions, which are meaningless in another Runtime.
        - **lazy entries**: the ids of the lazy entries the request Runtime adopted
        (@plan.LazyFeatures.O4); never module specifiers.
        - **envelope**: format tag "flow-state/hydration.v1", app id, app fingerprint, scope,
        request token, sequence, capturedAt (server epoch milliseconds), and an omitted list
        (item ids and reasons only, never values).

        Encoding: each item is encoded with the Schema that already owns it (definition Memory,
        resource result, stream value, entity fields) inside a Flow-owned envelope Schema, then
        written with the shared bounded structural codec of @plan.Inspection.O2: depth 32, 10,000
        nodes, 4,096 array items, 262,144-byte strings (owner decision 16). The encoded form must be
        JSON-safe. An item is omitted, never coerced, with reason:

        - **NotEncodable**: its Schema's encoded side is not JSON (Schema.instanceOf(File)), the
        resource has no result Schema (Dispatch Desk's openCount), or one value exceeds a
        per-value codec bound (the detail names the bound).
        - **Sensitive**: see redaction below.
        - **LocalActor**: a local actor reached by selection.

        Omission reasons are details on the dehydrate trace event, not diagnostic codes. Order is
        canonical: actor ids by byte order, entries by descriptor id then canonical key bytes
        (@plan.Operations.O1), so equal runs give equal bytes, on every host (Node, Bun, Deno,
        browsers).

        Identity: the app fingerprint is the digest of the internal representation that
        inspect(app) compiles (@plan.Inspection.O1). A payload never outlives a deploy, so the
        structural fingerprint is exact and needs no author version.

        Redaction (@D3): sensitive data never enters a payload. A sensitive entity field is dropped
        from its record, so the client store does not hold it and a reader that needs it fetches it
        (entity-domain.md section 5.5, "dropped from the base"). A resource entry or stream lane
        whose Schema contains a sensitive field is omitted whole. An actor whose Memory contains
        one is omitted, and so is every consumer that depends on it through context. The reason is
        Sensitive. This supersedes the SSR clause of owner decision 4.

        Size: maxBytes bounds the UTF-8 length of the serialised envelope. Over the bound,
        dehydrate rejects with FlowError(DehydrateTooLarge), whose details list the ten largest
        items by encoded bytes. No partial payload is ever returned.

        In-flight work at the captured cut:

        - **lookup in flight, no data**: the lane binding only, entry absent, listed unsettled;
        the client renders the lane Pending and looks up on activation (the server lookup was
        interrupted, so this is not a duplicate).
        - **refetch in flight over data**: the entry with its data and age; the client refetches on
        activation only if staleTime says so.
        - **lookup failed (Failure, Defect, Interrupted)**: entry absent, no error value sent; the
        client renders Pending without data and the activity retries. The actor's own state (for
        example DEGRADED after ListUnavailable) transfers as it was.
        - **events queued in a mailbox**: dropped and counted in DehydrateUnsettled; never
        delivered.
        - **commit in flight**: the actor's pending-commit facts, so the client restores the commit
        as unknown with its attempt (@plan.Operations.O3), and one DehydrateCommitInFlight warning
        is emitted. prepare should not cause commits; mutations belong in server actions or on the
        client.
        - **domain prediction live**: the confirmed base only.
        - **schedule armed**: its remaining time (@O5).

        Capture reuses the persistence capture algorithm (@D6): one consistent actor and store cut
        and pending commits as unknown. Only the selection and the destination differ.
        NonDurableContextProvider does not apply, because hydration takes the closure whole. A
        ConcurrentCapture conflict is retried inside dehydrate up to 3 attempts in total, then
        rejects with FlowError(ConcurrentCapture).
        Reference: none yet (stage S10 adds it).
    O4  Hydrate boundary and the no-mismatch rule
        <Hydrate payload={payload}>{children}</Hydrate> is a client component in flow-state/react.
        It must sit under a FlowProvider, else it throws FlowError(HydrateOutsideProvider) in
        render. It never suspends, renders its children unchanged, and may be nested and repeated
        (one per streamed segment, one in a layout plus one in a page).

        Phase 1, in render, silent:

        1. Look up the payload by (request token, sequence). If this Runtime has decoded it before,
        reuse that decoding; otherwise check and decode it once. An app id or fingerprint mismatch
        drops the payload with HydrationIncompatible; a decode failure, an undeclared lazy entry
        id, or an envelope over the codec bounds drops it with HydrationMalformed. Both are
        diagnostics, not throws: the fallback is ordinary client loading. A scope or request-token
        violation throws (@O6).
        2. Build the payload's server view: an immutable store view of its entries, records and
        answers, plus a snapshot per actor. Each snapshot is the same pure projection on both
        sides: state and memory from the payload; context selected from provider snapshots in the
        same chained view; lanes projected from bindings and entries in the view (an entry missing
        from the view gives a Pending lane without data); lifecycle active; issues empty. An actor
        of a lazy entry not adopted in this Runtime is held encoded and projected on first
        resolution with the machine its ref carries (@plan.LazyFeatures.O4).
        3. Provide the server view to descendants through React context, chained to the server
        views of ancestor Hydrate boundaries, nearest first.
        4. Insert into the live Runtime every item absent from it, as provisional, without
        publishing. No subscriber is notified during render, and no evidence is emitted.

        Phase 2, in the commit, before any descendant hook's attach in the same commit: publish
        phase 1's insertions as one store version; merge items that were already present under
        @O5; report phase 1's diagnostics; then activate the inserted actors, at once if the Runtime
        is ready, otherwise as part of the bootstrap (@O5). Hydrated actors pass the normal
        admission validation of @plan.Runtime.O3 (provenance, wiring, compatible providers,
        headroom) before phase 2 installs anything; a failure rolls back the whole payload, reports
        HydrationRejected with the admission diagnostic as its cause, and leaves the page on client
        loading.

        A render that React discards leaves phase 1's provisional insertions in the live Runtime.
        They are data only: no subscription, ownership, fiber or work exists for them. A
        provisional actor that no later phase 2 or attach installs is activated by the next
        bootstrap and is then subject to its retain like any unused shared actor.

        H1, the no-mismatch rule: during server rendering and during hydration, what a Flow hook
        returns is a function of the component's props and the payloads of its ancestor Hydrate
        boundaries only.

        - useView's getServerSnapshot resolves the actor in the chained server view, nearest
        boundary first, and applies the selector to that snapshot. descriptor.get and Entity.get
        on that snapshot read the same view.
        - The lookup form useActorByRef(ref) resolves against the chained server view during
        server rendering and hydration, so it is null on both sides for an actor in no ancestor
        payload; after hydration it reads the live Runtime (@plan.React.O2).
        - An actor in no ancestor view resolves to the pre-attach snapshot of @plan.React.O2,
        whose context reads only providers in the ancestor views. It is a pure function of the
        ref, the input and those views.
        - On the server React calls only getServerSnapshot, so the HTML obeys H1. While hydrating,
        React calls getServerSnapshot with the same inputs, so there is no mismatch. Afterwards
        React compares getSnapshot (the live store) and re-renders where it differs: a restored
        draft, newer client data or a client fetch appears one commit after hydration, never as a
        mismatch.
        - Streaming order does not matter: a component sees only its ancestors' payloads, never a
        sibling segment's, so selective hydration in any order gives the same result. A component
        above every Hydrate renders the pre-attach value on both sides.
        - Nothing time-dependent is in a server view: freshness is not part of a lane and stale is
        cause-based, so Date.now cannot cause a mismatch.
        - Every useView in one render under one boundary chain reads one immutable view, so the
        one-version rule of @plan.React.O1 holds.
        Reference: none yet (stage S10 adds it).
    O5  Precedence
        "Present" means present in the live Runtime when phase 2 runs.

        - **shared actor present** (active, disposing, restored, or a mirror in a follower tab,
        @plan.MultiTab.O2): the client wins; the hydrated actor is ignored (evidence skipped:
        present). An ensure with a different input keeps first-input-wins (@plan.Runtime.O3).
        - **resource entry present, no optimistic write pending, no lookup in flight**: the younger
        wins: replace when the payload's age at hydration is less than the client entry's age,
        otherwise skip.
        - **resource entry with a pending optimistic write or an in-flight lookup**: skip; fencing
        already orders the client's own work.
        - **entity record field, versioned**: the store's ordering rule: a strictly greater version
        replaces, a lower one is rejected, an equal one falls through to the unversioned rule.
        - **entity record field, unversioned and present**: keep the client value; if the payload
        value differs the field is contested, and the contested-field rule refetches the loader
        and the answers holding it.
        - **entity record field absent on the client**: filled.
        - **entity answer present**: the client wins; if the payload's references differ the
        client answer is marked stale with cause hydrate.
        - **entity answer absent**: inserted fresh, unless since ready() the client accepted any
        base delta, live prediction, uncertain mark or queued write on that entity, in which case
        it is inserted stale with cause hydrate.
        - **stream lane present**: the client wins.
        - **client predictions**: untouched, replayed over any new base.

        hydrate joins the closed cause list of entity-domain.md section 5.2 and lowers the frontier
        of the answers it covers, as restore does (@plan.EntityDomains.O1).

        Bootstrap merge. On a first page load the order is: phase 1 inserts during the hydration
        render; FlowProvider's effect calls ready(); the bootstrap acquires storage, reads and
        validates persisted data detached (@plan.Runtime.O2, @plan.Persistence.O4); then, before
        actors are installed, it merges restored data with the provisional hydrated items:

        - **actors: persisted beats hydrated**. A ref present in both is restored from storage and
        the hydrated copy is discarded before it ever activates (evidence superseded: restored).
        The UI shows the server's editor during hydration, then the restored draft one commit
        later. There is no content-based exception (@D5).
        - **data: hydrated beats persisted**. Restored entries and records are at position 0 and
        older by construction, so hydrated entries win; for versioned records the version rule
        decides.
        - **context**: a hydrated consumer whose provider is restored reads the restored provider.
        A restored consumer whose provider exists only in the payload is valid for this session.
        - After the merge, hydrated actors are installed as restored: no initial, no input, no
        events, no finite work replayed; context baselines are silent; activities reconcile next.
        From then on hydrated actors with persist: true are captured like any other.

        Activation without duplicate fetches or replay:

        - **ages are skew-limited**: age at hydration = age at capture + max(0, clientNow -
        capturedAt). A client clock ahead makes data older (it refetches sooner); a clock behind
        adds nothing. Freshness is then the ordinary staleTime rule (@plan.Operations.O2):
        Dispatch Desk's ticketList (10 seconds) does not refetch on activation unless more than 10
        seconds have passed. Recommend staleTime above the expected time to interactive.
        - **activities reattach by identity** (slot, descriptor, canonical key). When equal to the
        hydrated binding, the activity binds the hydrated entry, and because the payload records
        the entry version it last mapped, its value outcome (the editor's TicketLoaded) is not
        delivered again. A newer client entry version does deliver. When the identity differs (a
        restored provider changed context), the binding is released and the new one looks up or
        binds as usual.
        - **streams** always open a new session (no replay); the lane shows the hydrated latest
        value until the first new one arrives.
        - **schedules** re-arm with remaining = max(0, remaining at capture - max(0, clientNow -
        capturedAt)); one at 0 fires once on activation, never a burst (owner decision 10);
        restartOn keeps its captured baseline, so it does not fire on entry.
        - **retain** of a hydrated shared actor starts at activation, as for any actor with no
        uses yet.

        Client navigations render a new Hydrate with a new payload under a ready Runtime: phase 1
        inserts absent items silently, phase 2 merges present ones under the rules above. A payload
        the router cache replays has the same (token, sequence) and is a no-op. A payload
        prefetched long before it renders is aged by capturedAt.
        Reference: none yet (stage S10 adds it); app/persistence.ts shows the browser setup whose
        restore the merge joins.
    O6  Isolation guards
        - **one request Runtime per call** (@O1): no actor, entry, token or fiber is shared between
        dehydrate calls. Compiled machines may be cached per machine object across Runtimes,
        because compilation is pure; nothing else is shared.
        - **the render Runtime**: client components rendered on the server cannot see
        server-component scope, so the provider wrapper constructs a fresh render Runtime per
        request render (@plan.React.O1). It is never readied on the server (effects do not run), so
        it builds no Layer, opens no storage, coordinates no tabs and starts no work. It holds only
        decoded payloads and is garbage when the render ends; dispose() on a never-ready Runtime is
        a no-op.
        - **request token**: each payload carries one. Under the react-server condition dehydrate
        takes it from React cache(), so every segment of one RSC request shares it; otherwise each
        call gets a fresh token. Tokens are 128-bit random values (seeded in Stories); sequence
        numbers start at 0 per token in call-start order. A Runtime on which ready() was never
        called accepts payloads of one token only; a second token throws
        FlowError(HydrationCrossRequest) in render and applies nothing, naming the fix (construct
        the Runtime inside the provider, never at module level). A server-side module singleton
        therefore fails on the second request instead of showing one user another's data. In the
        browser FlowProvider calls ready() in its first effect, so later navigations with new
        tokens are accepted.
        - **scope lock**: a Runtime with persistence accepts only payloads whose scope equals
        persistence.scope; a Runtime without persistence locks to the scope of the first payload
        it accepts. A mismatch throws FlowError(HydrationScopeMismatch) in render and applies
        nothing from that payload. The recipe for a principal change stays a new Runtime under
        <FlowProvider key={scope}>. Flow checks that both sides agree on scope, not that it is
        true.
        - **server-only route**: flow-state/server maps the react-server and node export conditions
        to the real module, and browser and default to a stub that throws
        FlowError(ServerOnlyImport) on import, so a client import fails the build or the first
        load, never silently (@plan.Package.O1). Only the capture side (settle, selection,
        redaction, size bound, encoding) lives there; the hydrate side ships in the client bundle.
        - **tab coordination**: never selected by API presence on a server (@O1,
        @plan.MultiTab.O8).
        Reference: none yet (stage S10 adds it).
    O7  Next.js integration
        The App Router recipe, which the Dispatch Desk Next.js host proves (owner decision 20):

        - **server setup**: a function from the caller's token to runtimeSetup({ app, services })
        with no persistence; services are per request because they carry the token.
        - **browser provider**: a "use client" component that constructs the browser Runtime once
        per mount with useState(() => setup(scope).construct()) and renders
        <FlowProvider runtime={runtime}>. On the server it runs once per request render and builds
        the inert render Runtime of @O6; in the browser once per page load.
        - **root layout** (server component): awaits the host's authentication, calls dehydrate
        for the document-wide actors (the session), and renders the provider with
        <Hydrate payload> around children.
        - **segments**: each async server component that needs data calls its own dehydrate and
        wraps its client subtree in its own Hydrate, inside a plain React <Suspense> boundary for
        streaming. No Flow hook takes part in Suspense: Flow hooks never suspend.
        - **server decisions**: redirect() and notFound() are decided by calling operations or
        services directly in the server component (@D2).
        - **plain React SSR**: the same three calls with renderToPipeableStream and hydrateRoot;
        the payload travels in bootstrapScriptContent. Escaping "<" as < in the serialised
        payload is the host's one obligation (Next.js does it for RSC props).

        Client navigation, router-cache replay and prefetching follow @O5. The route layout of
        flow-state/server and the "use client" boundary of flow-state/react are @plan.Package.O1.
        Reference: none yet (stage S10 adds it).
    O8  Evidence, inspection and tool rules
        - **trace events**: dehydrate (selection, omitted items with reasons, unsettled items,
        bytes, attempts) and hydrate (per item one fate: inserted, merged, skipped with the rule
        that decided, superseded, contested; plus payload-level drops). Both are bounded like
        every event and carry digests per @plan.Inspection.O5; payloads hold no sensitive values.
        Phase 1 emits nothing; its findings are reported in phase 2.
        - **inspect(runtime)** adds hydration: accepted payloads (token, sequence, scope, bytes)
        and the provenance of each hydrated actor and entry (@plan.Inspection.O1).
        - **flow check** (@plan.CommandLine.O5): error when a Story .hydrate(source, label) names a
        label the source Story never dehydrates; warning when a resource that a shared actor's
        activity subscribes to has no result Schema (scoped per @Q1); warning when an actor
        selected for hydration has sensitive Memory fields, since it will never hydrate.
        - **Stories** (@plan.Testing.O7): .dehydrate(label, { scope, within, maxBytes? }) on a
        story.app runs the real settle on the TestClock and the real capture, records the payload
        at run.payloads[label] and keeps the Runtime running; .hydrate(source, label?) applies a
        payload exactly as Hydrate does. A hydrate before every other command runs before the
        bootstrap (a first page load); a later one runs on the ready Runtime (a navigation).
        Checkpoints carry hydrate evidence and serverView(label), the H1 view. Seeded ids and equal
        TestClock epochs make payload bytes golden. flow story run runs a hydrate Story's source
        Story first.
        Reference: none yet (stage S10 adds it).
decisions
    D1  SSR hydration is in scope for version 1
        Owner decisions 30 and 33; reverses the SSR clause of FlowState D50 and the sentence of
        FlowState O7 that put it out of scope, and minimal-library section 10's deferral. React
        Suspense integration stays out: no Flow hook suspends. Two public names are added,
        dehydrate (new route flow-state/server) and Hydrate (flow-state/react), plus two Story
        commands; nothing else is new.
    D2  dehydrate owns a private request Runtime
        Owner decision 30, accepting server-rendering.md Q1 for version 1. A host-owned request
        Runtime has no disposal hook in React Server Components (cache() scopes but never
        disposes), so open streams and polls would leak fibers. Pages that must decide on the
        server call their API directly. Revisit only if Next.js exposes a request-end hook.
    D3  Sensitive data never enters a payload
        Owner decision 30, superseding the SSR clause of owner decision 4, and server-rendering.md
        Q2. HTML is cached, logged and shared, so a payload is treated as an artifact. There is no
        opt-in for faithful sensitive hydration: it would be a name whose only use is weakening a
        guarantee, and the cost of omission is one client fetch.
    D4  H1 is the one render rule; views are ancestor-only
        From server-rendering.md section 2.6. A hook's server and hydration value depends only on
        props and ancestor payloads, never on sibling segments, the live store or the clock. It
        replaces the archived rule that the client Runtime be seeded and ready before hydrateRoot
        (archived ReactAndHosts O4), which streaming cannot satisfy.
    D5  Persisted beats hydrated for actors; hydrated beats persisted for data
        server-rendering.md section 2.8 and Q7. An actor is workflow truth and may hold an unsaved
        draft; data at position 0 is older by construction. No content-dependent exception.
    D6  One capture and install engine shared with persistence
        Capture and install reuse @plan.Persistence.O3 and @plan.Persistence.O4: consistent cut,
        closure, unknown commits, no-replay install, silent baselines. Hydration is a new selection,
        destination and precedence merge, not a second engine. Hydration is never a public mutable
        method on the Runtime: the frozen package's dehydrateBoot and hydrateBoot are prior art
        only (FlowState C2) and stay deleted, as do the archived construction-scoped seeding
        authority and runtime-boot payload.
    D7  maxBytes defaults to 256 KiB
        server-rendering.md Q6: 262,144 bytes of encoded JSON per payload; a larger page splits into
        segments, which also streams better. Measure in the proving app.
    D8  No server mode
        server-rendering.md Q3: one production execution path. The request Runtime opens stream
        sessions like any other; settle ignores them and dispose closes them inside the call. If
        the cost bites, a machine gates the activity with when on a session flag.
    D9  The first render outside a payload is the pre-attach snapshot
        Owner decision 29, settling server-rendering.md Q4 in the form @plan.React.O2 states: the
        selector applied to a pure pre-attach snapshot (default states, initial(input), lanes
        Pending or placeholder, context from provider snapshots in the ancestor views). The design's
        alternative of lanes undefined and context absent is not adopted.
constraints
    C1  Nothing escapes a request
        No request Runtime, render Runtime state, token, adopted set or decoded payload is
        reachable from another request. Module-level Runtimes on the server are detected
        (HydrationCrossRequest), not tolerated.
    C2  Render stays inert
        Phase 1 and every server render register no subscription, ownership, fiber, schedule,
        persistence write or evidence. Only phase 2 and attach effects create live state.
    C3  No silent loss
        Every item not transferred is listed with a reason; over-size payloads reject whole;
        unsettled capture is reported.
verification
    V1  H1 property
        Generated trees of nested and sibling Hydrate boundaries over the Dispatch Desk components,
        with every hydration order of the segments: renderToString, then hydrateRoot in jsdom with
        a second fresh Runtime, gives zero onRecoverableError calls and zero console hydration
        warnings, on React 18 and 19. Planned.
    V2  Cross-request isolation
        Two concurrent dehydrate calls with different scopes and interleaved fixtures share no
        actor, entry or token. A module-level render Runtime receiving two requests' payloads
        throws HydrationCrossRequest on the second, and the first request's data never appears in
        the second's HTML. The request Runtime selects solo tab coordination on a host with
        BroadcastChannel and navigator.locks present. Planned.
    V3  Scope
        A payload with the wrong scope throws HydrationScopeMismatch and applies nothing; a
        persistence Runtime rejects a payload for another scope; the keyed provider recipe remounts
        cleanly. Planned.
    V4  Settle and golden bytes
        Chained activities settle as a unit; streams and schedules do not hold it open; within
        expiry yields the documented unsettled payload and one DehydrateUnsettled; a send cycle
        ends at within; the same Story gives identical payload bytes on every run and on Node, Bun,
        Deno and a browser. Planned.
    V5  No duplicate fetches
        Counting fixtures prove zero lookups on activation for fresh entries, exactly one for
        unsettled, failed or NotEncodable ones, and a refetch exactly when the aged entry passes
        staleTime, including a client clock ahead of and behind the server. Planned.
    V6  No replay
        TicketLoaded is not redelivered on activation; a newer client entry version does deliver;
        schedules fire at the captured remaining time on the TestClock; a schedule past due fires
        once; restartOn does not fire on entry; a commit in flight at capture becomes unknown with
        its attempt. Planned.
    V7  Precedence
        One Story per rule of @O5, including a persisted draft beating a hydrated editor, a
        follower-tab mirror beating a hydrated actor, hydrated data beating persisted data, the
        unversioned contest, and a hydrated answer marked stale after a client prediction. Planned.
    V8  Redaction
        A sensitive field in an entity, a resource result and actor memory never appears in the
        payload bytes (byte search), the dependent consumer is omitted, and the matching omissions
        appear in the dehydrate evidence. Planned.
    V9  Size, options and failure lanes
        Over maxBytes, dehydrate rejects with DehydrateTooLarge and the top-10 detail, with no
        partial payload; each invalid option rejects with DehydrateOptionsInvalid before
        construction; a persistent setup rejects; an async prepare rejects with
        DehydratePrepareReturnedWork; a throwing prepare, a readiness failure, a capture failure
        and a disposal failure each dispose exactly the request Runtime and reject with the
        documented FlowError and cause; ConcurrentCapture retries 3 times then rejects. Planned.
    V10  Entity property suite
        The property suite of @plan.EntityDomains.O4 gains a hydrate step: dehydrate model A at a
        random point, hydrate it into model B mid-run, and check C1 to C8 on B. Planned.
    V11  Packaging
        A packed-consumer check: a browser bundle importing flow-state/server fails with

    V12  Next.js proving app
        Dispatch Desk on the App Router with the layout and segment boundaries of @O7, run in

questions
    Q1  Should the "no result Schema" flow check rule always warn?
        It is noise for browser-only apps. Recommended: warn only when the app is listed with
        ssr: true in flow.config.ts, or when the resource is used by a persist: true ref, which
        merges it with the persistence concern of @plan.Persistence.O2.
    Q2  Should scope be unified with principal() and persistence.scope?
        Three strings must agree by convention today. Recommended: yes, in a follow-up: one
        principal field on runtimeSetup that persistence scoping, principal() and hydration all
        read. It touches @plan.Persistence.O1, so it is not decided here.
