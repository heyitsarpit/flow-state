# Scope inventory: DiagnosticsContract, CommandLine, ProjectDelivery

Sources read in full: workflow/plans/archive/rewrite/DiagnosticsContract.plan, CommandLine.plan,
ProjectDelivery.plan (CommandLine links archive references/README.md, which only indexes the old
reference app; its tools/cli.ts was checked). New documents: workflow/plans/flow/FlowState.plan
(FS), references/design/minimal-library.md (ML), references/design/entity-domain.md (ED, sections
1-9 normative), references/dispatch-desk (DD: tools/cli.ts, tools/diagnostics.ts,
tools/inspection.ts, app/host.ts, flow.config.ts). SurfaceSimplification (SS) was consulted only
where FS D10/D11/D43 say "kept from" it.

Note on reference-only evidence: DD comments (for example the exit-code block in tools/cli.ts) are
marked "KEPT (ref only)" when FS itself is silent. FS C1 says the plan wins and archived rules are
not implied; a comment in a reference app is weak authority, so most such rows still recommend
stating the rule in FS.

Status legend: KEPT, CHANGED, DROPPED-EXPLICIT, DROPPED-SILENT. Recommendation: RESTORE,
CONFIRM-DROP, or "-" when no action is needed.

## Archived material relevant to SSR hydration, lazy loading and multi-tab persistence

- PD O3 Stage 5: "SSR waits for persistence". Stage 4 calls the restore path "no-replay hydration",
  so the archived design made SSR hydration reuse persistence capture and restore (consistent cut,
  no replay, uncertain commits restored as unknown). FS O8 keeps all of those restore guarantees.
- PD O2/O3: the "construction-owned setData authority" seam between Resources O4 and ReactAndHosts
  O4 (contract agreed in Stage 3, host adapters in Stage 5). That is the host-side store seeding
  entry point SSR needs.
- DC D3: ConcurrentCapture is the one retryable capture-conflict code, and "ConcurrentDehydrate" is
  explicitly retired as a label. Server dehydration should reuse capture and ConcurrentCapture,
  with no second code. NonDurableContextProvider (terminal), IdentityVersionMismatch, CodecFailure,
  MalformedData and StorageFailure are the codes a hydration payload and a shared multi-tab store
  need.
- DC O2: foreign Promise adaptation and AbortSignal forwarding (owned by ReactAndHosts O4) keep the
  complete Cause. A Next.js server boundary should follow this rule.
- DC O6 UnadmittedMachine ("include the machine in the app before runtime construction") and the
  closed AppPlan conflict with lazy features. The deleted module codes (DuplicateModuleOwnership,
  MissingModuleReference) are the shape a lazy entry needs: a lazy entry not yet loaded, or loaded
  twice with different content. Admission's exact-provenance checks (FS O3) must apply when a lazy
  machine arrives.
- CL O1: trusting gateway code and loading it under the project root. A lazy entry
  (ML decision 2: `lazy(() => import(...))`) must still be resolvable by the CLI so graph, check and
  explain see it statically.
- SS O6 (not assigned, found while checking FS D11): operation data and error Schemas are required
