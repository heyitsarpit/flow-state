## How the change flows through the system

- **One fixture module, four readers.** A composite part is a machine in the production API plus a user model and
  a server model. The generator reads it to emit scripts as JSON. The Spec model reads the script to compute the
  expected reports and world requests. Production replays the script under oracles. The benchmark replays it with
  no oracles and must produce the same work fingerprint. A new feature therefore costs one part edit, one model
  section and one production change, and every existing generated run re-judges it for free.
- **A new oracle re-judges everything.** Once composites run under generated scripts, an oracle added in a later
  slice (WriteAhead, Restore, Actors, Reads) immediately judges every earlier composite's runs. That is why slices
  that add oracles (2, 4, 5) come early and why hand cases stop growing.
- **Round-14 leaves the critical path.** Expected results come from the model (T45). Proof before production comes
  from model mutation: a part is useful if changing a model table cell changes its expected trace (advisor Q3).
  Round-14 keeps its 147 mutants on the 99 hand cases, behind a limits list that a run verifies. No composite is
  authored twice.
- **"No fixture tests a missing feature" becomes a check.** Each runtime adapter declares the feature codes it
  implements. The generator draws only commands whose codes the runtime declares. The matrix gate fails a part that
  claims a code no runtime declares. A part lands in its composite in the slice that builds its first feature and
  gains operations as later slices land theirs, as the catalogue's tiers intended.
- **The interleave rule moves from area to slice.** Inside each slice the suite half (Spec change, model section,
  parts, model mutation, audit) is finished before its production half starts. The Epic's
  "an area's suite is green, null-red, mutant-proven, reviewed and audited before its production module starts"
  holds per slice (question 2).
- **Production's lanes change shape once, before policies.** `latest`, `serialize`, `cancel` and `cancelAll` added
  to today's chain of `if`s would make the implicit state machine AGENTS.md forbids (advisor Q10 risk 4). Rewriting
  the lane first, under the unchanged suite, means slice 1 adds table rows, not branches.

## 3. The new Task order

### The slice template

Every slice is one Task, in this order, with one builder per half (the user's rule on builders):

1. **Spec:** the change from part 2, with its Invariants.
2. **Model:** the Spec model's section for the slice. It imports nothing from a runtime, and hand expectations
   drafted from the Spec by another author agree with it. A second model family reads a sample (T45's rule).
3. **Parts:** the composite parts the slice unlocks, plus operations added to parts already built. Each part has
   usual and stress profiles and joins the app mix.
4. **Proof before production:** model mutation shows the parts' generated runs kill table-cell changes; the suite
   half is audited. This is the interleave gate.
5. **Production:** built test first against model-predicted runs, through `index.ts` and the listed seam. The
   slice's capability codes are then declared, and the first-contact reds are classified (advisor Q8).
6. **Benchmark replay:** the slice's measures from catalogue section 6, replayed from the same scripts with a
   matching work fingerprint.
7. **Gates:** pair coverage for the slice's codes, with dated waivers only for codes in later slices; falsify,
   liar and core mutants on production; the coverage and matrix gates.

## 4. Risks and open questions for the user

1. **Composites run on production and the model only.** Round-14 keeps the 99 hand cases as a mutant host behind
   `limits.ts`. No one-source spike, and no composite authored twice. Recommendation: yes. The cost: composites
   lose round-14's 147 mutants, so core mutants, model mutation and the liar gate must carry strength. T51 and
   T45 are measured on those.
2. **The interleave rule is per slice, not per area.** The Epic line changes to "a slice's suite half is green on
   the model, mutant-proven by model mutation, reviewed and audited before its production half starts".
   Recommendation: yes.
3. **One Task per slice,** merging each suite and production pair as in the ledger. Recommendation: yes. It halves
   the hand-offs and keeps every Plan link.
4. **What counts as a fixture for the matrix gate.** A composite part, a static case, an example-app check or a
   package check, so that React, ServerRendering, Package and CLI features can be covered. Recommendation: yes,
   with the kind recorded per row.
5. **Hand cases freeze.** No new hand case except to document a ruling. The 99 cases become model tests and named
   examples, and Pay is not converted into a composite. Recommendation: yes.
6. **A reference derived from `Compiled`.** On composites, the selection oracle reads handler tables that the
   compiler under test produced. Recommendation: accept, and run the Compile static cases on every composite's
   `Compiled`. With question 1 there is no second compiler to disagree with.
7. **T51 before slice 1,** a behaviour-preserving rewrite of about 1,000 lines judged by the unchanged suite.
   Recommendation: yes. The alternative, doing it inside slice 1, mixes a refactor with four new policies under one
   set of reds.

   first would judge persistence from the start, but its oracles are all owed today. Recommendation: lanes first.
   Durability's oracles then re-judge every earlier composite run.
9. **T15 and T23 move to slice 6,** before streams, entities, multi-tab, lazy and tooling. Recommendation: yes.
   The core Specs are all built by then, and the old order put T15 before every production module.
10. **The real host persists nothing** (`host/browser.ts:22-25` has no store). Recommendation: an in-memory host
