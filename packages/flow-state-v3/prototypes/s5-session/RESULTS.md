# S5: does a stream session's state (Streams T1) live in the world step, or in a fiber in the driver?

Status: proposed, throwaway. Everything below is what `bun main.ts` printed (kept in `out.txt`; 0.7 s, Bun 1.4.2, effect 4.0.5).
Files: `shared.ts` (harness, scripted source, virtual clock, the turn), `formA.ts`, `formB.ts`, `main.ts` (scenarios, comparison, mutation, cost).

## Inputs and conditions

- **Compiled data in, no definition layer.** A contract is `Cfg { catchUp, reconnect, idleMs, healthyMs, flapMax, closeMs, fills?, backoff(n) }`. The source is scripted: connection k plays `conns[k]` (frames `live{head|proof|restartAt}`, `value`, `ping`, `down`, `fail`, `end` at a delay after open; past the script it is silent), and `read(from, next, no)` answers a `catchUp` with `more`, `done` or `gone` pages. Same `Scn` object for every form. Virtual clock, ties broken by insertion order; mailbox latency 1 ms, read latency 5 ms, scope close 3 ms.
- **Form A** (`formA.ts`, 176 lines): `stepA(cfg, state, input, now) -> [state, commands]` is pure. Commands: `open`, `close`, `arm`, `disarm`, `read`, `abort`, `mail`. The driver (about 20 lines) executes them and feeds frames, timers, pages and turns back as inputs.
- **Form B** (`formB.ts`, 159 lines): one real Effect fiber per session (`Effect.runFork` on a stepping scheduler). T1's variables (`n`, `flaps`, `liveSince`, `regIn`, `noted`, `owed`, `greeted`, `claim`, `buf`, `lastRead`, `prevNext`, the connection id) are locals. The fiber waits on its inbox with a virtual-clock deadline (`idle` and `healthy` are that deadline), sleeps the backoff (`Waiting`), and release is `fiber.interruptUnsafe()` with the connection closed in `ensuring`. The delivery queue `Q`, `inFlight`, `want` (next page wanted) and `sess` are closure state shared with the turn callback.
- **Shared (`shared.ts`, 103 lines incl. harness):** `applyTurn`, the world step both use: memory upsert, the bookmark's move (Streams T3), `settle`, the end-of-turn `filled` rule (placed: set from the field; the releasing turn: may raise, never lower; unplaced: nothing). The world holds `messages` (the `fills` field), the bookmark `{at, filled}` and an evidence log.
- **Streams table subset built** (T1, T2, T3, T4 for `every`): `connect` with the wipe check, `register` and T2 rows 1 to 7, values per state, `down`/`Dropped` with `owed`, `fail`/`end` -> `lose` with the default backoff and `Flapping`, `idle`, `healthy`, `Feed.ping` (does not re-arm in `Connecting`), repair (`more`, `done`, `gone`, buffer during the read, `settle(through ?? lastRead ?? greeted)`, next page only after the queue drains), release in any state with discard evidence, `clear`, `clearRelease` (one turn), reload (the runtime dies; only `messages` and the bookmark survive).
- **Named scenarios (15)** from the spec and the desk: connect and register with `every`; first open with `catchUp` and a value arriving during the read; drop and reconnect with and without `proof`; repair after a drop with a buffered value; release while waiting; ping and `idleTime`; reload restoring the bookmark; clear while placed, `ClearAndClose`, clear while unplaced; desk activity's `reset` -> `restartAt` (`features/Tickets/feed/feed.socket.ts`: `hello` echo -> `proof`, `reset` -> `restartAt`, `ping`); presence typing (`features/Presence/presence.contracts.ts`: `every`, no position, no `reconnect`, SDK `down`); `Flapping`. Each has a `want` written **by hand from machine-design.md 2.11.11**, not from either form.
- **Seeded interleavings:** 600 seeds x catchUp {off, on} x reload {no, yes} = 2,400 runs per form. Each draws connection 0 (a `live`, 1 to 3 values at 6 to 19 ms so ties are common, a `fail`), connection 1 (a `live`, with or without `proof`, 0 to 2 values), connection 2, a release at 10 to 29, 100 to 129 (the backoff), 105 to 129 (just after reconnect), 300 or none (20% of them `clearRelease`), maybe a `clear`, tie order within a connection shuffled, and whether external events are scheduled before or after the form's. Coverage of A's runs: 988 with a notice, 1,943 with a reconnect, 1,076 with a catch-up read, 1,611 ending released, 102 with discards, 0 ending `Ended` (that is only in the named `Flapping` run).
- **Variants of B:** `B-sync` (the fiber writes the world at once), `B-queued0/1/3` (the fiber's writes to the world land 0, 1 or 3 ms later, as a write through the Runtime's step queue would), `B-rand7` (the Effect scheduler drains its ready tasks in seeded random order, one seed only).
- **Compared per run:** delivery log (values, items, notices, failures, clears, in turn order), discarded list, the `from` of every `open`, bookmark `at` and `filled`, row, memory ids.

## Results

1. **Named scenarios:** A, `B-sync`, `B-queued0/1/3` and `B-rand7` all match the hand-written expectation in all 15 (after I corrected my own expectations in four places, below).
2. **Seeded interleavings, difference from A over 2,400 runs:** `B-sync` 0, `B-queued0` 0, `B-rand7` 0, `B-queued1` 1, `B-queued3` 576 (bookmark `at` 512, `from` of an open 42, log 21, `filled` 1). Invariants (below) flagged nothing in any unmutated run.
3. **What makes `B-queued` differ.** At 3 ms the fiber's `settle` write lands after a later value's turn, so the bookmark ends at `through` (6) instead of at the last delivered value (4); that is the order T3 asks for (a settle is "at the queue's head"), so a fiber that writes bookmark moves as separate inputs, not in the delivery queue, gets it wrong. The one `B-queued1` run (seed152CR, a reload) differs in `from` and a notice: a write was still pending when the runtime was cut, so the saved bookmark was older than the one A saved. That cause is my reading of the trace, not separately checked.
4. **Lines:** A 176, B 159, the shared turn plus harness 103, `main.ts` 197. Both are far under 500. B is about 10% shorter. Lines that mention `filled`/`fills`/`wiped`/`releasing`/`unplaced`: A 12, B 13, plus 9 in the shared turn.
5. **Reads across the boundary** (dynamic, over the 15 named runs and 800 seeded runs; same four sites in both): `b.filled` 1,530, `b.at` about 1,530, `b.exists` 1,512, `field.empty` 1,669 reads, of which 42 (0.7%) were taken while a delivery was queued or in flight (`b.exists` 19 and `field.empty` 19 at `register`, `b.at` 4 when a `live` restarts a repair). They read admitted state by definition (T2 is over what was admitted), so a pending delivery is not a hazard for either form as long as the read is synchronous. In B the world also reads fiber state at three places: `turn` reads `sess` (admit or discard), `ext` must publish `sess` before the turn that follows, and `ext("clearRelease")` must apply the clear as a releasing turn before interrupting. Nothing in B blocks on a read in `B-sync`, but `connect`'s wipe write must land at once (T1 says "at once") and the result for `B-queued` says why.
6. **Cost per delivery, Bun only,** 20,000 values, median of 7, unforced GC, wall clock, harness included: floor (frame event plus mailbox event, no session) 0.39 us, A 1.20 us, `B-sync` 1.35 us. The gap between A and B is inside what one run of this kind can tell apart.
7. **Mutation sanity**, injected into A's driver and checked against `B-sync`, against the hand-written expectation, and against two invariants (I1: no more notices than connections; I2: with `catchUp` off and one phase, every emitted value is delivered or discarded). Over 315 runs: none 0 flagged by any check; **dropped delivery** (the 2nd value's turn replaced by a no-op) flagged by the differential in 96 runs (94 had two or more values, the rest are reload runs where the mutation fires in phase 2), by the expectation in 10 of 15 named, by I2 in 70; **double notice** flagged by the differential in 91 runs (88 had a notice), by the expectation in 6 of 15, by invariants in only 3 (I1 is weak: it is a count, not an attribution). The differential and the expectation are what catch a double.
8. **`fills`, cleared versus wiped,** with the wipe check switched off in both forms (four clear and wipe scenarios): the log is the same; the only difference is the `from` handed to the source on the next connection (`-` when wiped, the bookmark when not), so what the trim loses is silent in the delivery log and visible only in what the adapter was asked. That is the documented silent-loss case.

## What each form made easier or harder

- **The question's two readings.** A is atomic: a step reads the bookmark and the field and writes both, and a reload cut sees all or none of it. B-sync is equal in behaviour only because the fiber's reads and writes of the world are synchronous calls; with the writes behind the step queue it diverges (result 3). So B does not remove the second owner of state: it needs the world to be written synchronously from inside a fiber, which is the reentrancy care Q3 names, and a shared `Q` between fiber and turn callback.
- **Where B is better.** Waiting, release and the deadline are three lines each (`sleep`, `interrupt`, a timeout on `take`) and `ensuring` makes "abandon the read, close the scope" one place. In A the same facts are `arm`/`disarm` commands, a connection id to drop stale frames, a read id to drop stale pages, and the guard in `timer`. B also needed no stale-input guards for timers (the cancel is the interrupt), but it still needed the connection id and the read id for frames and pages already in its inbox.
- **`fills`.** Neither form made it easier or harder: both need the same three pieces (connect's wipe check, the end-of-turn rule in the world step, and "a releasing turn may raise, never lower") and both need the turn to know the session's placement. A gets that for free in one step; B publishes `sess`. The compound `ClearAndClose` turn is the only place order mattered (clear as a releasing turn, then interrupt). The mechanics survive in about 12 lines per form plus 9 in the turn, and matched four hand-derived expectations. This spike cannot say whether `fills` survives S15: the seven exceptions of 2.11.8 and the silent-loss cases are not modelled and nothing here counts "High" findings in real code.

## Recommended form (proposed)

**A: T1 as data in the world step.** Evidence: identical behaviour in 2,400 interleavings (B only with synchronous writes), 176 versus 159 lines (not meaningfully shorter), no measurable cost difference, a reload cut that is atomic by construction, and B's fiber still shares five pieces of state with callbacks (`Q`, `inFlight`, `want`, `sess`, the world). B wins only on the three waits, which are about 10 lines either way. This is review 3.4's own criterion ("a wait or value lives in the core only if a rule makes it observable"): the bookmark and `filled` are observable by rule 71, and T1's reads of them are the entanglement. A hybrid, as the real code does (below), is the natural fallback: keep the data in the world and the connection handle and timers in the driver, which is what Form A's driver already is.
Caveat for the owner: the comparison is behaviour and size, not debugging, error reporting or bundle shape; and B was written second, copying A's structure, so B's lines are likely an underestimate of a naive fiber.

## Table findings (the divergences were about my transcription, not the forms)

- **T2 row 6 with `catchUp`:** the cell reads "stalls >= 3: notice(Lost), Live. C: Repairing from p. Else notice(Unproven), Live." I first coded a notice before the repair and both forms agreed with each other and disagreed with the hand-written expectation. Read as no notice with `C`, consistent with 2.11.10 ("With it, nothing extra"). The cell should say so.
- **Row 7 with `catchUp`:** coded as always one notice (no record and a filled field); the same rule 2.11.10 states.
- **Bookmark may end behind what is displayed** (a `through` ahead of a buffered live value): T3 says "last delivered wins, may move backward, safe". Seen in the model; duplicates only.
- **No head on the wire:** every reconnect of a feed with no `head` and no value yet notices once ("Flapping" run: two notices, then `Flapping`), as 2.11.10 says for the desk's `hello`.

## Compared with real code

- `codebases/tanstack-query/packages/query-core/src/subscribable.ts` and `queryObserver.ts` (`onSubscribe` lines 95-107, `destroy` 131-136), `query.ts` (`addObserver` 351-360, `removeObserver` 362-380): the lifecycle is a count of listeners; the first subscribe attaches the observer to the Query and starts the fetch, the last detaches and the Query decides what to cancel and when to collect. The live handle (`#retryer`) is a field on the Query, the data is `state`. Neither holds a fiber; nothing is a transition table. This is closest to a hybrid: data plus a driver-held handle.
- `codebases/xstate/packages/core/src/actors/callback.ts` (lines 195-237): `callbackState` (`receivers`, `dispose`) is in a module-level `instanceStates` map keyed by the actor, and the snapshot holds only `status`. `observable.ts` (lines 192-218): the subscription handle is a field inside the snapshot (`_subscription`) and `getPersistedSnapshot` strips it, `restoreSnapshot` sets it undefined. Both: observable state in the snapshot, the live handle outside it or removed on save, which is Form A's driver plus data. `sendBack` ignores messages after `stopped`: the stale-input guard Form A needs.
- `codebases/db/packages/db/src/collection/subscription.ts` (fields at 186-240, the setup comment at about 503): one object with plain mutable fields (`loadedInitialState`, `snapshotSent`, `_status`, `unsubscribed`) and an explicit note that adapter callbacks "may reenter" during setup. Reentrancy during setup is the same hazard as B's synchronous world write.

## Unverified

- Real network, real `AbortController`/`signal` plumbing, a real Clock (`TestClock` was not used; the virtual clock is mine), a browser's timer throttling, ordering of a timer against a socket message on wake.
- Whether the wipe, clear and `filled` inference holds in real apps (S15's trigger); only the mechanics are exercised.
- One seed of the random Effect drain order (`B-rand7`); other seeds were not run, so "fiber scheduling order did not matter" is for that one seed.
- A blocking delivery fiber (one that awaits each turn's end before pulling) was not built; B's `Q` is shared with a callback instead. That variant would remove the shared `Q` and make the idle deadline mean "pull outstanding" for free, and could change the result.
- The hand-written expectations are my reading of the tables; two of them I corrected after seeing the forms disagree with them (row 6, the ping scenario's horizon, a read-data inconsistency in one scenario, the flapping notices), each time against the spec text, not to fit the output.
- Per-delivery cost is one process, one machine, unforced GC; the harness copies state in A (`{...state}`) and the world step is shared, so absolute numbers mean little.
