# Inspection

Inspection shows how an app is built and what it did, through static checks, `flow explain` and read-only snapshots, without running application callbacks or gaining authority to act.

## Example: a verb that disagrees with its mapping

`Stripe.intent` maps only `success`, so the machine may look it up but not subscribe to it. The declaration is an error.

```ts
// checkout.definition.ts
// Stripe.intent is a resource declared once in stripe.ts with key: ["intentId"].
operations: ({ E }) => ({
  read: Stripe.intent.outcomes({
    success: E.Intent,            // maps success: lookup only (rule 41)
    failure: E.ReadFailed,
  }),
}),

// checkout.machine.ts
CARD: {
  on: {
    Pay: {
      target: S.READING,
      // one-off read: O.read.lookup(select) in actions
      actions: [O.read.lookup(({ event }) => ({ intentId: event.intentId }))],
    },
  },
},
READING: {
  // VerbMismatch: subscribe on an operation that maps success
  activities: [O.read.subscribe(({ memory }) => ({ intentId: memory.intentId }))],
},
```

## Example: check and explain from the shell

The check reads declarations and prints findings; explain prints what one event does from one state.

```sh
flow check --app checkout        # errors exit 1; warnings alone exit 0
flow explain checkout           # argument form is not fixed in the design
```

```text
Toggle  READY → READY; commits like (Issues.setLike, latest, one lane per Issue key)
```

## Keywords

### VerbMismatch

**What:** A declaration error when one operation uses the wrong verb for its mapping: `lookup` on an operation that maps `value`, `subscribe` on one that maps `success`, or two verbs on one operation.

**Why it exists:** An operation is either one-off or live, so its verb must agree with its mapping and with every use of it (rule 41).

- Status: 2.7.16 still marks it proposed, but the accepted list under OD24 includes it. For untyped code, `flow check` reports it from the tokens.

<small>Source: machine-design rule 41, 2.7.3, 2.7.16; OD24 accepted list</small>

### flow check

**What:** The CLI command that checks the complete declared graph, including lazy entries, without running any application callback.

**Why it exists:** It catches invalid declarations, wiring and ownership before a Runtime or Story runs, since findings cannot certify runtime callbacks.

- Each finding has a severity, a stable rule reason, its actual path and help text. Warnings alone do not fail the check.
- Unfilled optional guards and bare writes are listed as info.

<small>Source: CommandLine O5; machine-design 2.7.16, 2.9.5</small>

### flow explain

**What:** A static explanation of a machine's possible transitions, denials and commits, drawn from the summary without evaluating guards. With `--trace` and `--at`, it answers from recorded evidence instead.

**Why it exists:** A reader can see what an event does, and which lane it takes, without reading closures.

- Output is one line per transition, as in the example above.
- The design does not fix the argument syntax of the static form; the example shows only the output shape.

<small>Source: machine-design 2.7.16, 2.10.14; CommandLine O1, O4</small>

### lanes

**What:** A write lane is one serialized channel for a server call, identified by (actor identity, contract id, key); a one-off read has one lane per operation and incarnation.

**Why it exists:** Writes to the same server thing queue or hold on one lane, so an in-flight or unknown write blocks only its own lane.

- Inspection lists every lane with its operation path, subject path, and whether it is unplaced or releasing.

<small>Source: machine-design rules 21, 42, 51; 2.7.13; Inspection O1, C51, C64</small>

### orphans

**What:** A write lane whose operation is gone, or whose key no longer decodes under the contract's key Schema; it goes to the descriptor's `orphaned` handler, outside any actor.

**Why it exists:** A version change can remove an operation while its server call is still in flight, and the call still needs an owner to retry or cancel it.

- `orphaned: ({ attempt, retry }) => retry(attempt)` is the one place an Attempt is retried by argument.
- A lane whose path no incarnation has is unplaced and parks its endings on the lane record; Inspection lists it.

<small>Source: machine-design rules 46, 53, P19, C62; Inspection O1</small>

### records

**What:** One evidence record per Runtime decision, in one sequence starting at 1 across all kinds: turn, lifecycle, lane, ending, life, session, and more.

**Why it exists:** Records let an agent order what happened across machines, operations and persistence, and a Story run keeps them as its trace.

- A rolled-back turn leaves one turn record with result `failed`; a committed turn's records have contiguous sequences.
- The design extends the plan's kind list (C79) with `ending`, `lane`, `life`, `callback`, `exit`, `session`, and for Story runs `step`, `request`, `control`, `verdict`.

<small>Source: Inspection O4; machine-design C79, 2.10.14</small>

### UnresolvedHold

**What:** An error when a write on `reject`, `latest` or `serialize` maps anything but `unknown`, or when a branch keeps the hold and reaches no `retry` or `cancel`; a warning when the owner exists but is unreachable.

**Why it exists:** Every hold has an owner, so a server call with an unknown result cannot stall its lane with nothing able to end it.

- Arrivals are every leaf a new incarnation can be in while the lane is unresolved (2.7.14); the check runs inside each fragment and again at the host.
- The hold stays the default: no quiet release and no automatic retry (OD6).

<small>Source: machine-design rule 45, 2.7.14; OD6, OD10</small>

### KeyOmitsInput

**What:** A warning that a resource's `input` has a field that changes the output but is not in its `key`.

**Why it exists:** Cache entries are keyed by `key`, so a field left out of it would alias two different server answers.

- Streams are exempt: a resume position is an input field outside the key by design (OD12).
- A paged resource puts its page cursor in `key`, since each page is its own entry.

<small>Source: machine-design rule 39, 2.7.16; R7 K19 (proposed; in the OD24 accepted list)</small>

### SharedContract

**What:** An error when one actor tree has two write operations on the same write contract, counting every fragment placement; a warning when `key: []` sits on a placement whose subject path is not empty.

**Why it exists:** One write operation per contract per actor keeps one write in flight per key by construction.

<small>Source: machine-design rule 40, F2, 2.7.16; C65</small>

### KeyRequired

**What:** An error when a key-less `retry`, `retryable` or `cancel` is used on a keyed operation outside a handler of an event that operation alone maps.

**Why it exists:** Without a key, Flow cannot tell which lane the call addresses, so the author names it.

- `idle` and `get` always take a key on a keyed operation.
- A key-less `O.x.cancel` in `whenAbandoned` is not an error: it names every lane of the incarnation's subject path.

<small>Source: machine-design rule 43, OD8, 2.7.3</small>

### DuplicatePlacement

**What:** A construction error when one live operation is placed in two states that can be active together, unless state tokens in their `when` arrays make the placements exclusive.

**Why it exists:** A live operation has one lane per placement, so two placements that can be active together would conflict.

<small>Source: machine-design rule 41, OD17 Q14, C40</small>

### static analysis

**What:** Checks that read declarations (type tokens, key field lists, operation mappings, summaries) and never run guards, callbacks, adapters or services.

**Why it exists:** Flow cannot know whether a callback is correct, so it checks the structure it can see and says so; closures are not read (R10).

- Deny codes come from declared types; if complete type facts are missing, the check fails rather than claiming completeness.
- `inspect(app)` follows the same rule: it compiles the App without running any callback, Layer or service.

<small>Source: CommandLine O5; Inspection O1, D2; machine-design 2.7.16, 2.9.5</small>

### Inspection

**What:** The read-only layer that reports an app's structure through `inspect(app)`, and a running Runtime's last committed cut through `inspect(runtime)`.

**Why it exists:** An agent or host learns the app and its evidence without gaining execution authority; observation never starts work or changes state.

- Where the plan and the design disagree, the design wins: its C78 adds `work` and `incarnations` to `inspect(runtime)`, and its C79 and C80 add record kinds and digests for sensitive values.

<small>Source: Inspection O1, O4, C1; machine-design C51, C78, C79, C80</small>

### CLI

**What:** The `flow` binary: `story list | describe | run`, `trace summarize | diff`, `graph`, `check`, `explain` and `diff --base`.

**Why it exists:** Scripts and agents can inspect and gate on it; output is text by default, with a JSON form, and `--app` and `--project-root` select what is read.

- Exit codes: 0 for completed commands and warning-only checks; 1 for checks with errors or trace differences; 2 for usage, loading or I/O failures; 130 for interruption after cleanup.
- The plan does not name the JSON output flag, and the design says nothing about the CLI beyond 2.10.14.

<small>Source: CommandLine O1, O3, O5; machine-design 2.10.14</small>
