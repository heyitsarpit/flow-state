# Definition

`definition({...})` declares an actor's id, states, events, internal events, memory and operations; the machine attaches behaviour to it.

## Example: two-factor sign-in

The password step, then a two-factor step with a per-challenge lockout, from machine-design 3.1.

```ts
// signin.definition.ts
import { definition, deny, Flow } from "flow-state"
import { Schema } from "effect"
import { Auth } from "./auth.contracts"                 // verifyCode and resendCode (2.7.3)
import { Countdown, Field, Lockout } from "./fragments"

export const LIMIT = 3

const sixDigits = (v: string) => /^\d{6}$/.test(v) || deny("CodeFormat", { length: 6 })

export const SignIn = definition({
  id: "Auth/SignIn",                                    // the definition's name
  states: [
    "PASSWORD",
    {
      // a node with traits is wrapped with Flow.state; its children are the leaves
      TWO_FACTOR: Flow.state(["ENTERING", "VERIFYING", "LOCKED_OUT"], {
        traits: {
          code: Field(Schema.String, { validate: sixDigits }),
          resendCooldown: Countdown({ length: "30 seconds" }).resumable(),
        },
      }),
    },
    "SIGNED_IN",
  ],
  events: {                                             // anyone may send these
    PasswordAccepted: { challengeId: Schema.String },
    Submit: {},                                         // {} = no payload
    Resend: {},
    BackToPassword: {},
  },
  internalEvents: {                                     // only the machine produces these
    CodeAccepted: {},
    CodeWrong: { challengeId: Schema.String },
    CodeExpired: {},
    CodeUnchecked: Flow.uncertain({}),                  // the "we don't know" kind
    ResendSent: {},
    ResendRefused: {},
    ResendUnsure: Flow.uncertain({}),
    StopWaiting: {},
  },
  memory: {
    challengeId: Flow.initial(Schema.String, ""),       // constant start
    error: Flow.initial(Schema.NullOr(Schema.String), null),
    struck: Flow.private(Flow.initial(Schema.Array(Schema.String), [])),   // hidden from views
  },
  traits: {                                             // placed traits, machine-design 2.3
    challenges: Lockout({ limit: LIMIT, length: "5 minutes" }).each({ of: "struck", max: 20 }),
  },
  operations: ({ E }) => ({
    verify: Auth.verifyCode.outcomes({                  // one lane per challenge (the contract's key)
      success: E.CodeAccepted,
      failure: {
        WrongCode: E.CodeWrong.from((_, { key }) => ({ challengeId: key.challengeId })),
        Expired: E.CodeExpired,
        NotSent: E.CodeUnchecked,
      },
      unknown: E.CodeUnchecked,
    }),
    resend: Auth.resendCode.outcomes({
      success: E.ResendSent,
      failure: { Throttled: E.ResendRefused, NotSent: E.ResendRefused },
      unknown: E.ResendUnsure,
    }),
  }),
})
```

## Example: checkout payment

One server payment as an operation, with each ending mapped to an event; the states the machine uses are listed here.

```ts
// checkout.definition.ts
import { definition, Flow } from "flow-state"
import { Schema } from "effect"
// Stripe.confirm is the contract (2.7.3); IntentStatus is its Schema, not shown in the design
import { IntentStatus, Stripe } from "./checkout.contracts"

export const Checkout = definition({
  id: "Shop/Checkout",
  states: ["CARD", "PAYING", "WAITING", "UNSURE", "STUCK", "READING", "DONE"],
  events: {
    Pay: { paymentMethodId: Schema.String },
  },
  internalEvents: {
    Intent: { status: IntentStatus, chargeId: Schema.optionalKey(Schema.String) },
    Declined: { code: Schema.String, paymentMethodId: Schema.String },
    Busy: { retryAfterMs: Schema.optional(Schema.Number) },   // no attempt field: Flow keeps the Attempt
    TooManyAttempts: {},
    Refused: {},
    TryLater: {},
    Unsure: Flow.uncertain({}),                               // the only kind unknown: may target
    TookTooLong: {},
    RetryNow: {},
    CheckTick: {},
  },
  memory: {
    intentId: Flow.input(Schema.String),                      // supplied by the creator
    paymentMethodId: Flow.initial(Schema.String, ""),
    busyTries: Flow.initial(Schema.Int, 0),
    retryInMs: Flow.initial(Schema.Number, 0),
  },
  operations: ({ E }) => ({
    pay: Stripe.confirm.outcomes({
      success: E.Intent.from((v) => ({ status: v.status, chargeId: v.chargeId })),
      failure: {                                              // exhaustive over the commit's failure tags
        CardDeclined: E.Declined.from((r, { input }) => ({ code: r.declineCode, paymentMethodId: input.paymentMethodId })),
        Busy: E.Busy.from((r) => ({ retryAfterMs: r.retryAfterMs })),
        TooManyAttempts: E.TooManyAttempts,
        Rejected: E.Refused,
        NotSent: E.TryLater,                                  // flow check requires it here (rule 20)
      },
      unknown: E.Unsure,                                      // StillUnknown arrives here too (rule 18)
    }),
  }),
})
```

## Keywords

### `definition({...})`

**What:** Declares an actor's shape: `id`, `states`, `events`, `internalEvents`, `memory` and `operations`.

**Why it exists:** Placement is structure, so the states, events and placed traits are typed before any behaviour is written.

- The machine attaches behaviour with `machine(SignIn, ({ S, E, O }) => { ... })` (3.1).
- The memory type is `SignIn.Memory.Type`; private fields are absent from it (3.1, 2.2.2).

<small>Source: machine-design 2.3 · 3.1</small>

### `id`

**What:** The definition's name, written first in the object, such as `"Auth/SignIn"`.

**Why it exists:** Tooling gets one label per definition, and the design's key order puts it first (2.6).

<small>Source: machine-design 2.6 · 2.2 · 3.1</small>

### `states`

**What:** An ordered list of leaf names and single-key nodes that hold children, giving every place the actor can be.

**Why it exists:** The tree is declared once in the definition, so `S` and the view types come from it (2.3).

- A plain compound is `{ TWO_FACTOR: ["ENTERING", "VERIFYING", "LOCKED_OUT"] }`; a node that carries traits is wrapped as `Flow.state(children, { traits })`; a subroutine goes in as `{ NAME: Sub }` (2.3).
- The machine names a child as `S.TWO_FACTOR.LOCKED_OUT` and tests it with `.is(state)` (3.1).

<small>Source: machine-design 2.3 · 3.1</small>

### `events`

**What:** The public events anyone may send, each a name mapped to a field record.

**Why it exists:** Views, other actors and the host need one list of what may be sent from outside (2.2).

- `Submit: {}` has no payload; `PasswordAccepted: { challengeId: Schema.String }` has one (3.1).
- A payload that needs a shape check is written `Schema.Struct(...).check(...)`; the check reads no memory, while a guard is policy (2.2.1).

<small>Source: machine-design 2.2 · 2.2.1 · 3.1</small>

### `internalEvents`

**What:** Events that only the machine produces, from its own schedules and from operation endings.

**Why it exists:** Timers and server answers enter as ordinary events, and no outside sender can produce them (2.2).

- Only the machine's own schedules and operations produce these; the `unknown:` target must be one of the `Flow.uncertain` events (2.2, 2.7.3).

<small>Source: machine-design 2.2 · 2.7.3 · 3.1</small>

### `Flow.uncertain(fields)`

**What:** Marks an internal event as the kind that an operation's `unknown:` may target.

**Why it exists:** An unknown ending means the request left and no trustworthy answer came back, so it gets its own kind (2.7.1).

- `StillUnknown` arrives at the same `unknown:` target (2.7.3, rule 18).
- Written as `CodeUnchecked: Flow.uncertain({})` inside `internalEvents` (3.1).

<small>Source: machine-design 2.2.1 · 2.7.1 · 2.7.3</small>

### `memory`

**What:** The actor's data as Schema fields, changed only by accepted transitions.

**Why it exists:** Each field says where its start value comes from, so starting memory stays pure and readable (2.2.2).

- Every field starts from exactly one source: `Flow.input`, `Flow.initial`, or absence for an optional key. A field with none is a type error (2.2.2).
- Disagreement: Machines O1 requires a top-level `initial({ input })` for nonempty memory (Machines.plan line 17). The design removes both top-level blocks (2.2.2), so the design wins.

<small>Source: machine-design 2.2.2 · Machines O1 (disagrees)</small>

### `Flow.initial(schema, value or fn)`

**What:** A field's start value: a constant, or a pure function of fields that start from `Flow.input` or a constant `Flow.initial`.

**Why it exists:** Creation runs once per incarnation and never on restore, so it must be pure, with no clock or randomness (2.2.2).

- A computed start, such as `Flow.initial(Schema.String, ({ title }) => title)`, cannot read another computed field (2.2.2).
- It is Schema's constructor default, restricted to plain values (2.2.2).

<small>Source: machine-design 2.2.2</small>

### `Flow.private(schema)`

**What:** A field that only the owner's handlers, guards and selects can read or write.

**Why it exists:** Counters and bookkeeping stay out of what the host and views depend on (2.2.2).

- Outside types omit it, but Stories and Inspection still see it. `Flow` stays outermost: `Flow.private(Flow.initial(...))` (2.2.1, 2.2.2).
- A host's `memory.<instance>.<field>` read of a private field is a type error (2.2.2).

<small>Source: machine-design 2.2.1 · 2.2.2 · 3.1</small>

### `operations`

**What:** Binds each server contract to this definition's events, as `({ E }) => ({ name: contract.outcomes({...}, { writes }) })`.

**Why it exists:** Each ending is mapped to an event here, and the machine decides only how the call runs (2.7.3).

- The second argument, `{ writes }`, receives `{ value, input }` and reads no memory; a domain write's `writes` may only invalidate (rule 36, 2.8.9).
- Two write operations on one write contract in one definition are a declaration error, `SharedContract` (2.7.3).

<small>Source: machine-design 2.7.3 · rule 36 · 2.8.9</small>

### `Flow.input(schema)`

**What:** A memory field that the creator supplies when it creates the actor.

**Why it exists:** The field's origin is written on the field, so no separate input block exists (2.2.2).

- The creator passes it, as in `useActor(Checkout, { input: { intentId: "pi_1" } })`. The definition's `Input` type is exactly the `Flow.input` fields; after creation they are ordinary, writable memory (2.2.2).
- Never combine it with `Flow.initial` on the same field (2.2.2).

<small>Source: machine-design 2.2.2</small>

### `hostEvents`

**What:** Events sent only by the direct host, with `raise`, to a trait or subroutine.

**Why it exists:** A host can drive a placed part without giving outside senders the same access (2.2).

- Only the direct host sends it, with `raise: [E.timer.Start]` as in 3.1's Countdown, so a view or an outside actor cannot (2.2, 3.1).

<small>Source: machine-design 2.2 · 2.6 · 3.1</small>

### `callbacks`

**What:** Moments that a trait or subroutine reports to its host, while the fragment carries on.

**Why it exists:** The fragment reports a moment and continues; the host writes the response (2.2).

- A transition names it in `notify: [callbacks.onDone]`; the host fills it with an `on`-style handler whose data is `payload` (2.2, 3.1).

<small>Source: machine-design 2.2 · 2.2.1 · 3.1</small>

### `Flow.optional(port)`

**What:** Lets a host leave a guard, callback or exit unfilled.

**Why it exists:** The author states which holes are allowed; a required port left unfilled is a type error (2.2).

- An unfilled optional guard allows, and an unfilled optional callback ignores (2.2).
- It marks a port, not a memory field; a memory field that may start absent uses `Schema.optionalKey` (2.2, 2.2.2).

<small>Source: machine-design 2.2 · 2.2.2</small>
