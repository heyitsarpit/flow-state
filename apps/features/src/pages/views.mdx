# Views

A view is a React component's read of one actor: `useView` gives it a frozen snapshot, `useNow` gives it the clock, and `actor.send` sends events back without starting work.

## Example: two-factor step

A component reads a sign-in actor, disables a button with `check`, and sends events. Hooks only; the form is in machine-design 3.1.

```tsx
// TwoFactorStep.tsx
import { check, type Actor } from "flow-state"
import { useNow, useView } from "flow-state/react"
import { SignIn } from "./signin.definition"              // user-defined: the definition, which exports S and E
import type { SignInMachine } from "./signin.machine"    // user-defined: the machine's type

const { S, E } = SignIn
const secondsLeft = (dueAt: number | undefined, now: number) =>
  dueAt === undefined ? 0 : Math.max(0, Math.ceil((dueAt - now) / 1000))

export function TwoFactorStep({ signIn }: { signIn: Actor<typeof SignInMachine> }) {
  const now = useNow("1 second")                         // epoch ms; re-renders every second
  const code = useView(signIn, (s) => (S.TWO_FACTOR.is(s) ? s.memory.code : null))   // state check narrows memory
  const error = useView(signIn, (s) => s.memory.error)
  const resendDue = useView(signIn, (s) => s.schedules.resendCooldown?.done?.dueAt)  // an unkeyed schedule's due time
  const canSubmit = useView(signIn, (s) => check(s, E.Submit())._tag === "Allowed")  // verdict only; publishes nothing
  const canResend = useView(signIn, (s) => check(s, E.Resend())._tag === "Allowed")
  const resendIn = secondsLeft(resendDue, now)

  return null                                            // the form renders code, error, canSubmit, canResend, resendIn
}

// the form's submit handler sends an event:
//   onSubmit={(e) => (e.preventDefault(), signIn.send(E.Submit()))}
```

## Example: issue list and row

A list reads its path lane and drafts from memory; each row reads a shared record and its own write lane. The row is keyed by the item it renders.

```tsx
// IssueList.tsx                                         // list: the actor handle; the List definition is user-defined
const rows = useView(list, (s) => s.operations.issues?.data?.issues ?? [])   // a path read; undefined while not placed
const drafts = useView(list, (s) =>
  s.memory.creating.filter((d) => !d.discarded && !rows.some((r) => r.id === d.id)),   // a draft never shows twice
)

// IssueRow.tsx                                          // issue: an item from rows; it carries id
const row = useView(list, (s) => Issue.get(s, { id: issue.id }, Issue.pick("title", "liked", "likes")))   // shared record
const saving = useView(list, (s) => List.O.like.get(s, issue).pending)        // this actor's like is in flight
// onClick={() => list.send(E.Toggle({ id: issue.id, liked: !row.data.liked }))}
```

## Keywords

### useNow

**What** Returns the Runtime clock's epoch milliseconds and re-renders the component at the given interval.

**Why it exists** Views read time through it, not `Date.now`, so Stories and `StoryFrame` control the clock.

- `useNow` is specified only in React.plan O4 (proposed) and used in the 3.1 example; machine-design has no separate section.

<small>Source: React.plan O4 (proposed) · machine-design 3.1</small>

### useView

**What** Subscribes a component to one actor and re-renders when its selected value changes; the selector receives a frozen snapshot.

**Why it exists** It is the only way a component reads actor state, and reading it never starts work or takes ownership.

- React.plan O4 says selectors read `context`, `issues` and `activities`; machine-design 2.7.5 and 2.7.16 say `s.operations` and `s.schedules`. The design wins.
- `useView` takes an exact actor handle, not a Machine or a ref; a nullable lookup must be branched first (React.plan O4, proposed).

<small>Source: machine-design 2.7.5 · React.plan O4 (proposed)</small>

### Snapshot `s`

**What** The frozen snapshot a selector receives: the state, `memory`, `operations`, `schedules` and `context`.

**Why it exists** Every `useView` read in one render sees one consistent version across actors and store entries, so a view cannot mix two moments.

- Fields declared `Flow.private` are missing from `s.memory` in views; Stories and Inspection still see them.

<small>Source: React.plan O1 and O4 (proposed) · machine-design section 5 table (Machines O8, React O4)</small>

### S.X.is(s)

**What** A state token's `is` tells whether the snapshot, or a state path, is in that state or below it.

**Why it exists** A view narrows by state before it reads state-specific memory or schedules, so the value it reads matches the state it is in.

- A guard array element passes when the pre-turn state is at or below it (Machines O2, a row in the section 5 table).

<small>Source: machine-design 3.1 · Machines O2 (section 5 table)</small>

### s.memory

**What** The machine's memory, written by its handlers: drafts, errors, toasts, reconcile keys and selection.

**Why it exists** It holds workflow state that the machine decides, and no shared data.

- Machine memory never mirrors entity data; records are read with `Entity.get`, not copied into memory.

<small>Source: machine-design 2.8.2 · 3.1</small>

### s.schedules

**What** Each schedule's row by name, such as `s.schedules.resendCooldown`; its `done?.dueAt` is the time it is due.

**Why it exists** A view can count down a cooldown or lockout from the schedule itself, not from a timer it keeps in memory.

- A keyed schedule is a list; find an entry by `key` and read its `timer` (3.1 uses `s.schedules.challenges.find(...)`).

<small>Source: machine-design 2.7.10 · 3.1</small>

### check(s, event)

**What** Runs the turn's steps 2–6 on an event and returns a verdict: `Allowed`, `Denied` with `reasons`, or `Unhandled`.

**Why it exists** A button can be disabled by the same rule that would refuse the press, so the view and the machine agree.

- `check` mints nothing, joins no queue and predicts nothing. A pre-commit defect comes back as `Denied` with code `InvalidTurn` (2.5).
- To refuse a second press as a whole turn, write `O.pay.idle(k?)` in the guard; a plain `reject` commit only refuses the write (2.7.3).

<small>Source: machine-design 2.5 · 2.7.3 · 3.1</small>

### actor.send(E.X(...))

**What** Sends one event from a view to an actor. Keyed events go through `E.<name>.key(k)`.

**Why it exists** A component changes an actor only by sending events, so the machine's handlers and guards decide every change.

```tsx
// InvitePage.tsx (excerpt)
<input onChange={(e) => signup.send(E.invites.key(f.key).Changed({ value: e.target.value }))} />
<button onClick={() => signup.send(E.RemoveInvite({ key: f.key }))}>Remove</button>
```

- A view may send `events` only. `hostEvents` come by `raise` from the host, and `internalEvents` come from schedules and endings.
- `flow check` reports a mapped operation ending sent from a view as an error (rule 47, 2.7.16).

<small>Source: machine-design rule 2 · rule 47 · 3.3</small>

### s.operations.x

**What** A write's lane row `{ pending, uncertain, waiting, retryCount, progress? }`, a one-off read's row, or a live placement's lane. Each is `undefined` while absent.

**Why it exists** The view shows "saving", "not confirmed" or "your newer edit waits" from the lane, not from memory.

```ts
const paying = useView(checkout, (s) => s.operations.pay.pending)            // unkeyed write
const hits = useView(search, (s) => s.operations.results?.data?.hits ?? [])  // one-off read
```

- `pending` is `InFlight`: the lane is sending. `uncertain` is `Held`: this actor's write is unknown, so a view shows "not confirmed".
- `waiting` means a never-sent commit exists behind the one in flight.

<small>Source: machine-design 2.7.5 · 2.7.13</small>

### Entity.get

**What** Reads an entity's shared record for a key: `Issue.get(s, key, shape?)` returns `{ data, predicted, uncertain, unconfirmed }`.

**Why it exists** Records are shared truth: every actor and view sees a server answer as soon as it lands, and a predicted write shows before the server confirms.

- `Issue.pick(...)` names the fields the view reads (2.8.2).
- `predicted` shows an unconfirmed write applied to every actor; `uncertain` marks an unknown one. "This actor is saving" is the lane, not the record.

<small>Source: machine-design 2.7.5 · 2.8.1 · 2.8.2</small>

### O.x.get(s, item)

**What** Reads one keyed write lane for the item a view renders. A key with no lane reads as idle, not `undefined`.

**Why it exists** A view asks "is this item saving?" without building a key record, and the same accessor works in a host's guards.

```ts
// a host view reads a fragment's write lane by key (rule 50)
const saving = useView(ws, (s) => Autosave.O.save.get(s, { docId }).pending)
```

- The item must carry every key field; a missing field is a type error. TypeScript is structural, so any record with an `id` type-checks against `["id"]`.
- Fragment lanes are read with `Fragment.O.x.get(s, k)` (rule 50, React O4).

<small>Source: machine-design 2.7.5 · 2.9.6 · 2.7.16</small>

### FlowProvider

**What** (proposed) `<FlowProvider setup={setup}>` constructs and owns one Runtime per setup scope; `<FlowProvider runtime={runtime}>` leaves construction and disposal to the host.

**Why it exists** Hooks find their Runtime from the nearest Provider, and a sign-out or account switch builds a fresh one.

```tsx
<FlowProvider setup={setup}>      // the Provider owns the Runtime
  <App />
</FlowProvider>
```

- Not met in the examples. machine-design has no Provider section; the hooks that use it are `useActor(machine, options?)` and `useActorByRef(ref, options)` (React.plan O2).
- Children render at once without suspending; the Provider's first effect calls `ready()` (React.plan O1, proposed).

<small>Source: React.plan O1 and O2 (proposed)</small>
