# User workflow coverage

Status: primary user-problem companion to the vNext contracts; not normative and not evidence of
shipped API

This document asks whether a developer can build, change, test, and operate an ordinary product
feature with Flow State. It starts from the work they are trying to complete, then uses XState,
TanStack Query, and Zustand as evidence for the recurring problems a state library must address.

Every Flow answer below is a vNext target until its phase proof is green.

## Decide whether Flow should own the state

Flow is useful when state has legal transitions, asynchronous lifetime, shared application
meaning, durable identity, or behavior worth testing as a story. It is intentionally expensive
for raw UI values because every Flow event is an ordered actor turn with immutable publication.

| State or work                                                               | Recommended owner                             | Why                                                                                                                                                                         |
| --------------------------------------------------------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hover, focus ring, uncontrolled input, animation frame, pointer coordinates | React, DOM, CSS, or a local ref               | Publishing every transient change through an actor adds ordering and allocation without adding domain meaning. Send a Flow event only when a semantic threshold is crossed. |
| URL path, search parameters, and browser history                            | Router                                        | The URL is already the durable owner. Route loaders or adapters may send typed machine events, but Flow should not maintain a competing URL copy.                           |
| Field-level form dirtiness and validation with no shared workflow           | React or a form library                       | A machine adds little until submission, cancellation, server validation, multi-step behavior, or cross-route drafts matter.                                                 |
| Shared draft, wizard, modal with acquired work, or resumable workflow       | Flow machine state and memory                 | Legal transitions and state-owned activities make cancellation, recovery, persistence, and tests explicit.                                                                  |
| Cached server read                                                          | Flow resource activated by a machine activity | The runtime can deduplicate, retain, invalidate, refresh, and project one canonical ref without component lifetime becoming cache policy.                                   |
| Server write, optimistic edit, or external command whose result matters     | Flow transaction                              | A transaction owns commit, concurrency, optimistic overlays, rollback, invalidation, and typed terminal evidence.                                                           |
| Continuing subscription or poll                                             | Flow stream activity                          | Scope, replacement, Effect Stream backpressure, and interruption remain owned even when components mount or routes change.                                                  |
| Long-running behavioral process                                             | Child machine                                 | The process keeps its own state, memory, activities, inspection, persistence identity, and completion evidence.                                                             |
| Theme or tiny preference with no workflow                                   | Host storage or a small external state owner  | Capturing a complete Flow runtime is disproportionate. Flow should integrate with this state, not claim all application values.                                             |

## The ordinary path for a new feature

A product feature should have one recognizable authoring path rather than separate query, store,
effect, React, and test implementations.

1. **Name the domain shape.** Add state tokens, event constructors, and fresh memory to one
   `definition`. This becomes the inference and durable-identity anchor.
2. **Declare external boundaries.** Create reusable resources for cached reads, transactions for
   writes, streams for continuing data, and child descriptors for independent workflows. Their
   `Effect<A, E, R>` requirements stay exact.
3. **Define legal behavior.** Bind those descriptors inside `machine(definition, callback)`.
   States own which work exists; events own why behavior changes; outcome mappings return async
   facts to the same mailbox.
4. **Publish a screen model.** A `view` selects one atomic actor snapshot into the values,
   operation snapshots, and capabilities a component needs. It does not start work.
5. **Expose the feature.** A module lists public root machines and views; app compilation infers
   their reachable descriptors and service requirements.
6. **Connect a host.** The browser, server request, router, or test owns runtime/actor lifetime.
   React uses `useActor` to send commands and `useView` to render.
7. **Write the behavior story.** Fixtures control real service boundaries, commands advance one
   deterministic plan, and named checkpoints become ordinary host-runner assertions.

This is more setup than a `useQuery` or Zustand store for a trivial component. It pays for itself
when reads, writes, cancellation, state transitions, persistence, and testing would otherwise be
spread across several unrelated owners.

## Building and changing UI behavior

| User task                                                     | Typical ecosystem pattern                                                                                                                                                                             | Flow workflow                                                                                                                                                                                                         | Verdict                                                                                                     |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Add a local input or visibility toggle                        | React state or a Zustand boolean/action                                                                                                                                                               | Keep it local unless its transitions or lifetime affect the application. If opening a modal starts work or closing must cancel it, model `CLOSED`/`OPEN` and let `OPEN` own the activity.                             | Covered, with an explicit rule against putting every UI value in Flow.                                      |
| Build a multi-step form or wizard                             | Zustand stores a `step`; XState uses compound states and guarded transitions                                                                                                                          | State tokens represent steps, memory retains submitted fields, guards own legal next/back actions, and activities own validation/submission.                                                                          | Flat wizards are direct. Nested, parallel, and history statecharts are excluded from vNext.                 |
| Run several independent branches and join when all finish     | XState parallel regions keep several configurations active and complete after every branch reaches final ([parallel workflow](../../../docs/codebases/xstate/examples/workflow-parallel/main.ts#L23)) | Several Flow activities may execute concurrently and route outcomes into one parent machine, which explicitly records and guards the join.                                                                            | Concurrent work and explicit joins are direct; atomic orthogonal regions are excluded.                      |
| Disable a command until it is legal                           | Duplicate UI predicates, XState `can`, or mutation status checks                                                                                                                                      | Put the rule in the transition guard and select `can(snapshot, exactEvent)` in the view.                                                                                                                              | Direct; duplicating a predicate in React is a bug.                                                          |
| Gate a feature by permission or prerequisite data             | Conditional rendering plus disabled query/mutation hooks                                                                                                                                              | Materialize the permission/prerequisite through a resource or typed event, make it part of the machine guard, and project the exact capability from the view.                                                         | Direct when the fact is already present; guards do not execute hidden asynchronous authorization work.      |
| Share feature state across components or routes               | A singleton Zustand hook or context store                                                                                                                                                             | A runtime-owned root survives component unmounts; several views may project different screen models from the same actor.                                                                                              | Direct, with heavier bootstrap and clearer lifetime.                                                        |
| Combine several feature roots on a dashboard                  | Read several stores/selectors                                                                                                                                                                         | Use several `useView` calls when separately published facts are acceptable. Facts that must change atomically belong under one actor; parent/child coordination remains mailbox-ordered across separate publications. | Covered compositionally; there is deliberately no cross-actor atomic view or commit.                        |
| Create many independent editors, rows, or dialogs             | Component-local XState actors or per-instance Zustand stores                                                                                                                                          | The app statically admits the actor family in `dynamicMachines`; a host creates or looks up a stable-ID instance and passes it to `useView(actor, view)`, while a parent machine may own one declared child.          | Direct for host-owned instances and restored lookup. Runtime-sized child activity collections are excluded. |
| Supervise a long-running upload, import, checkout, or runbook | Invoke/spawn a child actor and exchange events                                                                                                                                                        | `activity.child` owns exact input, lifetime, child snapshot, and one final settlement outcome while the child owns its resources, transactions, streams, and timers.                                                  | Direct for autonomous managed children. Ongoing commands use a host-owned dynamic actor instead.            |
| Handle raw scroll, drag, pointer, or animation data           | Zustand transient subscription or mutable refs                                                                                                                                                        | Keep raw values outside Flow and send semantic events such as `DragCommitted` or `BottomReached`.                                                                                                                     | Intentional non-goal; actor turns are for semantic facts.                                                   |

## Reading server data

| User task                                           | Typical TanStack Query workflow                                                        | Flow workflow                                                                                                                                                                                                                                                          | Verdict                                                                                                     |
| --------------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Build a basic list or detail screen                 | `useQuery`, then render loading/error/data                                             | A screen state owns `activity.observe(ref)` and a view returns the exact resource snapshot. The component renders its discriminants rather than generic machine-wide flags.                                                                                            | Direct, but the initial feature has more declarations than one hook.                                        |
| Share one result across several components          | Reuse one query key; mounted observers share a cache entry                             | Machine activities using the same exact ref join one runtime-store generation. Components read views; additional mounts neither retain nor refetch data.                                                                                                               | Direct with stronger work ownership.                                                                        |
| Build list-to-detail navigation                     | Separate list/detail keys and derive temporary detail from list cache                  | Within one actor that materialized the list ref, activate the exact detail ref and let the view temporarily select the list item. A separate detail actor must receive typed input/event data or use a coordinating parent; it cannot read another actor's projection. | Direct within one actor; cross-actor navigation requires explicit transfer rather than ambient cache reads. |
| Search or autocomplete with debounce                | Debounce input outside Query, change the key, cancel obsolete work, keep previous data | Events update the term, a machine timer owns debounce, the binding declines empty/ineligible terms, and exact-ref generations reject stale completion. Memory/view explicitly retain a previous useful key when desired.                                               | Direct; there is no `keepPreviousData` shorthand.                                                           |
| Load B after A and run a fixed group in parallel    | `enabled`, adjacent queries                                                            | Binding selectors return `null` until dependencies exist; several declared activities run concurrently.                                                                                                                                                                | Direct for fixed work. Runtime-sized fan-out uses an application aggregate or host-owned actors.            |
| Paginate or build infinite scroll                   | Page keys, `keepPreviousData`, or one infinite-query page array                        | Current page/cursor lives in memory and an aggregate resource owns the retained page window; a view selects the resulting projection.                                                                                                                                  | Direct through an aggregate. Per-page dynamic activity collections are excluded.                            |
| Prefetch a likely route or hover target             | Imperative `prefetchQuery` or router loader                                            | A typed hover/navigation/loader event activates finite `ensure`; later screen ownership reuses the exact ref. Server prefetch uses the same event path.                                                                                                                | Expressible. A router recipe or adapter would reduce ceremony without creating a new cache owner.           |
| Refresh in the background                           | Focus/reconnect refetch, interval polling, or manual `refetch`                         | Active `observe` authorizes stale focus/reconnect refresh; finite `refresh` handles explicit cycles; a scoped stream owns push updates or operational polling.                                                                                                         | Direct. Offline is advisory, and reconnect refreshes only active missing/stale refs without in-flight work. |
| Apply WebSocket/SSE changes to existing cached data | Subscription callbacks update or invalidate query entries                              | A scoped stream routes typed values to the actor and may cause exact invalidation/refetch; stream values may also enter typed events and machine memory.                                                                                                               | Direct without stream-to-cache writes; resource lookup remains the sole canonical base publisher.           |
| Keep data usable offline                            | Cached queries plus network modes                                                      | Retained canonical resource values remain readable; an application connectivity service/stream owns domain behavior while the runtime owns exact generations and reconnect facts.                                                                                      | Direct. Explicit work still admits and in-flight work continues; an outbox remains application-owned.       |

## Submitting and reconciling writes

| User task                                      | Typical ecosystem pattern                                            | Flow workflow                                                                                                                                                                                            | Verdict                                                                                                    |
| ---------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Submit a form and show progress/failure        | Mutation hook callbacks and status flags                             | A typed event enters the submitting behavior, `activity.run` starts the transaction, the view reads its exact snapshot, and routed outcomes move application behavior.                                   | Direct. User-visible recovery remains authored rather than inferred globally.                              |
| Optimistically edit several cached projections | Snapshot/write/rollback query caches                                 | One transaction preview applies ordered multi-ref overlays atomically; every terminal path removes only its generation and declared targets become invalidated.                                          | Direct with stronger overlap and cleanup semantics.                                                        |
| Prevent duplicate submits or resolve overlap   | Disable buttons, mutation scopes, ad hoc request IDs                 | Transaction concurrency selects `reject`, `cancel`, `allow`, or `serialize` per exact ref; `can` covers machine legality and the transaction snapshot covers admission/activity.                         | Direct, but views must expose both facts when the UI needs both.                                           |
| Cancel after navigation or a changed selection | Abort signals and effect cleanup                                     | Leaving/reentering the owning configuration releases its activity Scope; replacement allocates a new generation and rejects late completion.                                                             | Direct without a public cancel registry.                                                                   |
| Autosave a draft or enforce a deadline         | Debounced effects, mutation callbacks, or XState delayed transitions | A typed timer makes the cadence/deadline part of behavior and a transaction owns each save attempt, concurrency, and failure.                                                                            | Direct. Raw keystrokes may stay local while semantic draft changes enter Flow.                             |
| Use the server response immediately            | `setQueryData`, mutation response callbacks, normalized-store writes | vNext removes the preview and invalidates declared targets; active `observe` may refetch authoritative data, while a typed outcome may place returned IDs or receipts in machine memory.                 | Direct with a single canonical resource publisher. Authoritative transaction-to-cache writes are excluded. |
| Queue writes while offline                     | Persisted paused mutations                                           | Machine/domain memory owns a durable outbox, an application connectivity stream drains it, and story fixtures control connectivity. Pending transaction Effects are never serialized as executable work. | Application-owned by design; Phase 8 supplies the canonical proved recipe.                                 |

## Routing, host effects, and application integration

| User task                                   | Flow boundary                                                                                                                                                                                                  | Consequence                                                                                                                                 |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Change the URL after success                | Model success as machine evidence and let the router host translate that evidence into navigation, preferably through a route adapter or declarative redirect component.                                       | Flow does not acquire browser history as hidden transition work, but a canonical router integration recipe is needed.                       |
| Show a toast or banner                      | Put durable/actionable notification state in the machine and render it declaratively; keep disposable cosmetic toasts in the UI host.                                                                          | A toast library is not a transaction engine, and React does not need to own server work merely to render feedback.                          |
| Send analytics or an audit command          | Use a transaction when delivery/result matters. Public inspection buffers/artifacts may supply bounded Flow diagnostics, while application analytics remains a separate host integration.                      | Fire-and-forget anonymous machine actions remain excluded, and live custom telemetry streaming is not a public inspection protocol.         |
| Focus an element or invoke a platform API   | A component reacts to selected semantic state at the DOM boundary.                                                                                                                                             | DOM ownership stays with React; the machine records why focus is appropriate, not the mutable element handle.                               |
| Load a route on the server                  | A request runtime receives a typed preload event, waits for actor evidence, captures closed boot, and renders the prepared snapshot.                                                                           | The client installs the same boot before activity and must select the same first view.                                                      |
| Restore after reload                        | The host validates compatible v2 boot and application-owned domain migration before runtime construction. Active streams restart from persisted canonical params under a new Scope after hydrated publication. | Mutable rehydration and executable-fiber continuation are excluded; capture persists the complete canonical StoreState or fails explicitly. |
| Persist one small preference                | Keep it in host storage or a separate small state owner unless it participates in a Flow workflow.                                                                                                             | Whole-runtime capture should not become a replacement for every local-storage use case.                                                     |
| Synchronize another tab or external process | Adapt BroadcastChannel/WebSocket/filesystem events into a scoped stream or typed host event.                                                                                                                   | The transport stays application-owned while the machine owns how received facts change behavior.                                            |
| Sign out or switch account                  | Dispose the session runtime, await cleanup, then construct a new runtime for the next identity instead of invalidating and retaining old canonical values.                                                     | A proof-backed replacement recipe must show actors, resource bases, streams, and boot payloads cannot cross the identity boundary.          |
| Lazy-load a route or optional feature       | Import the complete module/app plan before constructing its runtime; a running runtime cannot register another root or descriptor.                                                                             | The boundary is closed: load before app/runtime construction or create a separate lazy-island runtime. Live extension is excluded.          |

## Testing, debugging, and changing an existing feature

| User task                           | Flow workflow                                                                                                                           | What correct looks like                                                                                                       |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Add a new state or event            | Change the definition, implement its machine behavior, update affected views, and add a story/checkpoint.                               | Exact tokens make missing transitions and stale view assumptions compile-time work instead of runtime string drift.           |
| Add a new API read or write         | Declare the descriptor, bind it to the owning state, expose its exact snapshot in a view, and control its Effect boundary in stories.   | Production and test execution use the same resource/transaction interpreter and lifetime.                                     |
| Reproduce a race or retry bug       | Author concurrent controlled outcomes, explicit `flush`/`settle`/clock movement, and checkpoints.                                       | The test asserts immutable evidence without sleeping, mocking actor internals, or mutating operation status.                  |
| Understand why an event did nothing | Use public transition analysis plus `attachInspectionSink(createInspectionBufferSink(...))` and its inferred projections.               | The answer identifies guard/transition facts and committed revisions without exposing a package-private TurnRecord stream.    |
| Review behavior before release      | Compare graph/behavior artifacts and execute registered stories through the real app runtime.                                           | Documentation, CLI behavior, and tests derive from the same definition and story values.                                      |
| Rename or split a feature           | Treat definition, member, descriptor, app, and persistence IDs as compatibility identity, then migrate artifacts intentionally.         | Refactoring TypeScript names cannot silently reinterpret persisted state or inspection history.                               |
| Test React rendering                | Render an already-owned runtime, drive actor events or stories, and assert the selected view.                                           | Strict Mode or component remounts cannot duplicate runtimes, actors, resource leases, or remote work.                         |
| Reset production state              | Send a typed domain reset/sign-out event or replace the owning runtime; stories instead receive a fresh scoped runtime for every run.   | Production cleanup follows real activity ownership, while tests never depend on a process-global mutable reset hook.          |
| Add a modular feature slice         | Add its root machine and views to a module and share descriptors or declared children through the static app graph.                     | Same-actor memory is atomic and child settlement is typed; an independently commanded workflow is a host-owned dynamic actor. |
| Initialize from SSR props           | Void-input roots receive request data through typed preload events or boot; exact constructor input belongs to dynamic actors/children. | Request state cannot leak through a singleton root or be fabricated by a component-owned store.                               |

## Remaining user-facing work

The primitive audit remains useful, but these are the concerns a feature developer will
actually feel:

1. **Simple features carry visible setup.** A basic cached list needs a definition, machine,
   resource binding, view, module, runtime, and story. The answer should be one canonical feature
   template and excellent inference, not a second hook-owned execution path.
2. **Repeated UI workflows need a host recipe.** Dynamic actors are intentionally not created by
   React, so routers/dialog managers need one standard create-or-lookup/pass/dispose pattern.
3. **Router integration is currently conceptual.** Preload, navigation events, URL ownership,
   request runtimes, and actor disposal have primitives but no canonical adapter or walkthrough.
4. **Offline outbox and persistence need canonical walkthroughs.** Their ownership and failure
   semantics are settled, but examples must prove one acquire/use/release path before publication.
